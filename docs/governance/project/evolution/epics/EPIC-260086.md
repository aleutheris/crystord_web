# EPIC-260086: Canvas delete affordances that mislead — bond removal, and the undo promise

- Epic ID: EPIC-260086
- Title: Canvas delete affordances that mislead — bond removal, and the undo promise
- Persona/Actor: Any user with editor or owner access deleting a bond or an atom.
- Value statement: For a user removing something, make the delete affordances tell the truth —
  either do what they say, or say what they do.
- Context: Found 2026-09-02 while writing user-facing help for EPIC-260080, which forced someone
  to read the delete paths end to end for the first time since they shipped. None of these is a
  regression; the help copy that described them has been corrected.
- Problem statement: Three defects on the delete paths.
  **(a) Bond removal is a silent no-op on both canvases.** `graph-types.ts:56,:77` build edges
  with `label: undefined` (label suppression is deliberate, ADR-260039 §D5), and
  `use-canvas-interactions.ts:103` matches `b.name === String(edge.label)` — against the literal
  `"undefined"`. `handleEdgeDelete` falls out at `if (!bond) return`: no call, no undo, no error.
  **(b) It also swallows atom deletion.** `use-canvas-interactions.ts:133-141` branches to
  `handleEdgeDelete` whenever an edge is selected, so pressing Delete with a line selected does
  nothing at all — not even the atom confirmation the user expected.
  **(c) Undo is lossy, and the dialog over-promises.** `handleUndo` calls
  `createAtom(title, labels)` only (`use-graph-data.ts:96-111` fills the rest with empty strings
  and a new uuid), so description, content, formula, categories, bonds, grants and identity are
  gone. Separately, `DeleteConfirmDialog.tsx:28` promises "can be undone briefly" on the
  Details-tab path, which sets no undo entry at all.
- Expected outcome: bond removal works or explains itself; Delete with a line selected does not
  swallow atom deletion; and the undo promise matches what the path delivers.
- Non-goals: not a redesign of bond editing or the canvas keyboard grammar; not a change to the
  label-suppression decision in ADR-260039 §D5.
- Dependencies: EPIC-260080 (found them); ADR-260039 §D5 and ADR-260034 (label suppression);
  ADR-260072 (Flow edge direction); ADR-260015 (delete safety and undo).
- Risks/assumptions: **`destroy` is a hard delete** — `DestroyOutcome { requested, deleted,
  notFound }`, with no `restore` or soft-delete anywhere in the schema. So "Undo" is a re-create
  and can only ever restore what the client held in memory; a faithful undo needs either full
  client-side re-creation (still partial — the new uuid breaks other atoms' inbound bonds) or a
  backend restore mutation, **which would be an ICR**. Unprobed: whether `destroy` cascades
  inbound bonds or leaves them dangling.
- Target window: TBD.
- Validation approach: unit — the right bond is removed for a selected edge on both projections,
  refused on a view-only source; Delete with an edge selected no longer swallows atom deletion.
  Each guard verified to fail without its fix.

## Ideation Bullets

- [ ] How an edge carries its bond identity without reintroducing visible labels — keep `label`
      and suppress at render, add a non-visual `data` field, or key off `edge.id`.
- [ ] Whether Flow should offer bond removal at all: its edges are a projection with inverted
      direction (ADR-260072), so "delete this edge" there means editing a formula's dependency.
- [ ] What Undo should promise. Three options, and the choice sizes the epic: full client-side
      re-create (partial by construction), a backend restore mutation (an ICR), or stop promising
      and remove the control. (b) cannot be resolved without answering this.
- [ ] Whether a silent `return` is ever acceptable on a destructive path — both the `!bond` guard
      and the access gate above it fail closed and say nothing.
