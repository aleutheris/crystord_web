# EPIC-260077: Resizable Left Rail — drag-to-widen the Explorer panel

- Epic ID: EPIC-260077
- Title: Resizable Left Rail — drag-to-widen the Explorer panel
- Persona/Actor: Any user browsing or organizing taxonomy/labels in the left-rail Explorer,
  especially the Categories lens
- Value statement: For a user classifying data with Categories, deliver a resizable left rail so
  deep or wide category trees are readable without truncation, wrapping, or horizontal scrolling.
- Context: The left rail (`LeftRail.tsx`) hosts the Labels/Categories navigator lenses at a fixed
  `240px` width. EPIC-260076 added dimension nesting on top of value nesting, so `CategoryTree`'s
  indentation (`indentOption`, 4 non-breaking spaces per depth level) now compounds two levels of
  hierarchy in the same fixed-width column — display names truncate or wrap sooner than before.
- Problem statement: Users have no control over the rail/canvas width tradeoff. A fixed `240px`
  rail that was adequate for a flat label list is cramped for a nested category tree, and there is
  no workaround short of a code change.
- Expected outcome: A user can drag the rail's right edge to widen (or narrow) it within sane
  bounds, and the chosen width persists across sessions the same way the existing collapse state
  does.
- Success metric(s): unit tests cover the resize/clamp/persistence logic; e2e coverage exercises a
  drag-resize and confirms the width survives a reload; qualitative — a deep category tree is
  legible at a user-chosen width without truncation workarounds.
- Non-goals: TBD by ideation — draft assumption is that touch/narrow-viewport-specific resize
  affordances are out of scope (no existing mobile breakpoint story in this app to hook into).
- Constraints: Must preserve existing collapse behavior (`leftRailCollapsed`) unchanged, and must
  not regress the shell's existing accessibility bar (ADR-260031: keyboard operability, visible
  focus indicators).
- Dependencies: EPIC-260066 (shell foundation — `LeftRail`, slot registries, `WorkspaceContext`),
  EPIC-260068 / EPIC-260076 (Categories navigator and its dimension tree — the direct motivator).
- Risks/assumptions: Assumes the existing `localStorage`-backed preferences pattern
  (`use-preferences.ts`) is the right persistence mechanism to extend, rather than a new mechanism.
- Target window: TBD.
- Validation approach: e2e drag simulation (pointer down/move/up asserting width change and
  persistence across reload) + keyboard-resize assertion if D2 below resolves to "yes"; unit tests
  on the width-clamp function in isolation.

## Ideation Bullets — Resolved (2026-08-27, plan review; approved by the project owner this date)

- [x] **Scope: left rail only.** Right rail (`Inspector.tsx`) is out of scope for this epic — the
  reported problem (Categories tree readability) is specific to the left rail, and generalizing to
  both rails without a validated need would double the surface area for no expressed benefit. The
  resize mechanism built here is expected to be reusable if the right rail needs it later.
- [x] **Width bounds: default `240px` (unchanged), min `200px`, max `480px` further capped at 60%
  of viewport width.** Below `200px` the lens switcher tabs and `CategoryNodeEditor`'s
  `width: '100%'` inline inputs get uncomfortably cramped. The `480px` ceiling is paired with a
  `60vw` cap (`min(480, 0.6 * viewportWidth)`) so the rail can't crush the center canvas on a
  narrow browser window, without building a separate narrow-viewport feature.
- [x] **Persistence: extend `use-preferences.ts`.** New `leftRailWidth: number` /
  `setLeftRailWidth` alongside the existing `leftRailCollapsed`, same localStorage
  read/write/try-catch shape and sticky-default caveat every other preference in that file
  already has. No server-side persistence — this is a cosmetic client-local layout preference, not
  a contract change.
- [x] **Keyboard accessibility: included in v1.** The resize handle is a WAI-ARIA `separator`
  (`role="separator"`, `aria-orientation="vertical"`, `aria-valuenow`/`min`/`max`, focusable):
  ArrowLeft/ArrowRight nudge the width by a fixed step, Home/End jump to min/max. Every other
  interactive control in this shell (`GraphViewTabs`, the lens switcher in `LeftRail` itself,
  `CategoryTree`'s tree role) is keyboard-operable — a mouse-only handle would be the first
  inconsistency of its kind, and reuses the same clamp function the pointer-drag path needs anyway.
- [x] **Reset affordance: double-click the handle restores the default `240px`.** Cheap, and the
  conventional pattern for this control (VS Code, browser devtools split panes).
- [x] **Granularity: one shared width for the whole rail, not per-lens.** A per-lens width would
  make the rail visibly jump when switching Labels ↔ Categories with no expressed need for it —
  the over-engineering trap this project's other ADRs have explicitly avoided (e.g. ADR-260039
  rejected building both LR/TB Flow orientations upfront for the same reason).
- [x] **Collapse interaction: independent state, no special-casing.** Collapsing hides the rail;
  expanding restores whatever width was last set (not the default). `leftRailCollapsed` and the
  new `leftRailWidth` are two independent preferences with no dependency between them, matching
  how `use-preferences.ts` already treats every other preference pair.
- [x] **Full code + test coverage task** — included (T4).

Given the keyboard-accessibility bullet's resolution, this epic ships its own T1 ADR (matching
every other shell-capability epic's precedent: ADR-260061, ADR-260066, ADR-260070, …) documenting
the bounds, persistence key, keyboard grammar, reset affordance, and single-width decision.
