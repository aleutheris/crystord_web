# EPIC-260084: Backend contract self-contradiction — arity metadata vs. guide, and undocumented error codes

- Epic ID: EPIC-260084
- Title: Backend contract self-contradiction — arity metadata vs. guide, and undocumented error codes
- Persona/Actor: Any client author of the Crystord backend — this frontend first, but the problem
  is in the contract, not in one consumer.
- Value statement: For a client building against schema 9.3.0, deliver one authoritative answer per
  question, so that reading the contract correctly cannot still produce a wrong client.
- Context: `docs/crystord_server/schema.graphql` plus the machine-readable metadata it publishes
  (`discoverOperations`, `collectQueries`) versus `docs/user-guide.md`. Surfaced while probing a
  live 9.3.0 server on 2026-09-01.
- Problem statement: **The two halves of the backend contract disagree, and each is wrong about a
  different operation — so a client cannot fix this by picking a side.** Measured with
  `tools/backend_probe/probes/operation_arity.py` against a live 9.3.0 server:

  | Operation | `discoverOperations` | `user-guide.md` | Observed | Wrong source |
  | --- | --- | --- | --- | --- |
  | `MINUS` | `maxArity: null` (unbounded) | ":1243 — "exactly two"" | `MINUS(10,3,2)` → `5.0`, success | **the guide** |
  | `DIVIDE` | `maxArity: null` (unbounded) | ":1283 — "exactly two"" | `DIVIDE(10,3,2)` → `failed-origin`, `OP-SIG-ARITY-MISMATCH` | **the metadata** |

  A client that trusts the guide breaks MINUS (EPIC-260083, a live data-loss bug). A client that
  trusts the published metadata breaks DIVIDE by offering an argument count the server rejects.
  There is no third source.

  **Second, smaller half: the guide is not an exhaustive error-code list, and nothing says so.**
  Three codes observed on a live server appear nowhere in it:

  | Code | When | Surface |
  | --- | --- | --- |
  | `OP-SIG-ARITY-MISMATCH` | `DIVIDE` with 3 args | evaluation (`failed-origin`) |
  | `AC-LABELS-EMPTY` | `change` with `labels: []` | write-time GraphQL error |
  | `AC-LABELS-INVALID` | label outside `[A-Za-z_][A-Za-z0-9_]{0,127}` | write-time GraphQL error |

  `errorCode` is an unenumerated `String` (`schema.graphql:255`), so no schema diff can surface a
  new code and no reader of the guide can enumerate them. The `AC-LABELS-*` pair also means
  `AtomInput.labels: [String!]!` cannot actually be satisfied with `[]`, which the type does not
  express.
- Expected outcome: one authoritative source per question, or an explicit statement of which wins.
  Concretely: the guide's MINUS/DIVIDE arity sentences and `discoverOperations`' `maxArity` agree
  with the evaluator, and the documented error codes are complete or declared incomplete.
- Success metric(s): `discover_operations.py` reports zero disagreements against a corrected
  contract; every code a client can encounter is either documented or covered by a stated
  fallback rule.
- Non-goals:
  - Fixing the client's MINUS truncation — that is EPIC-260083, and it can ship first.
  - Consuming `collectQueries` / `ConstantSpec` in the frontend (EPIC-260082's recorded follow-up).
    **This epic is a precondition for it, not part of it:** reading `maxArity` today imports a
    false bound for DIVIDE, so the registry follow-up must not proceed until this is settled.
  - Mapping the three codes into the client's `ERROR_SUMMARIES` / `ORIGIN_SENTENCES`. That is
    cheap and can be done independently; it is listed as an ideation bullet, not a blocker.
- Constraints: **the frontend cannot fix any of this.** The resolution is a backend change or a
  documentation change, so this epic's real output is a decision and an ICR conversation, not a
  code change in this repo. The pin is `~9.3.0`, so a corrected metadata answer likely means a new
  backend version and a fresh adoption ICR.
- Dependencies: ICR-260081 (the 9.3.0 pin whose adoption missed this); EPIC-260083 (the client-side
  symptom); EPIC-260082 (whose probing found it, and whose registry follow-up this blocks).
- Risks/assumptions:
  - Every observation here comes from ONE live server (`nucubuntunl`, `schemaVersion 9.3.0`) on
    one date. Re-run the probes before acting — a server-side fix may have landed since.
  - ~~`SUM` and `PRODUCT` were reported as `maxArity: null` and were **not** tested beyond the
    client's own assumption that they are variadic. They may hide the same DIVIDE-shaped defect.~~
    **Closed 2026-09-01:** both measured variadic and correct (`SUM/4 → 16.0`,
    `PRODUCT/4 → 60.0`). All five registered operations are now measured; `DIVIDE` is the only one
    the metadata gets wrong.
  - Assumes `discoverOperations`' metadata is *intended* to be authoritative. If the backend's
    position is that the guide wins and the metadata is advisory, that is a legitimate answer —
    but it must be written down, because a client reading `maxArity` has no way to know.
  - The undocumented-codes half may be a documentation gap rather than a contract defect, and may
    warrant only a note. Do not bundle its priority with the arity half.
- Target window: **Parked 2026-09-01** — not a priority, and the first open bullet is the backend team's call, not ours. Resume by asking which source they hold authoritative.
- Validation approach: `tools/backend_probe` is the validation surface — `discover_operations.py`
  diffs the tables, `operation_arity.py` settles a specific operation. Both are already written.
  A finding here becomes a client-side test only after the backend answer is known.

## Ideation Bullets

- [ ] **Which source is authoritative?** Get the backend team's position before proposing anything.
      The answer determines whether this is a guide edit, a metadata fix, or both.
- [ ] **Does this need an ICR?** If the fix changes what `discoverOperations` returns, it changes
      an interface this frontend reads, so probably yes. If it is only a guide correction, no.
- [x] **The untested operations are fine — the defect is `DIVIDE`-only.** Measured 2026-09-01:
      `SUM/4 → 16.0` and `PRODUCT/4 → 60.0`, both variadic exactly as `maxArity: null` claims and
      as the client already assumes. `MINUS/8 → 0.0`, also genuinely unbounded. So of the five
      registered operations the published metadata is wrong about **one**: it reports
      `DIVIDE maxArity: null` while a third argument is rejected with `OP-SIG-ARITY-MISMATCH`.
      That narrows the ICR considerably — this is one wrong field on one operation plus two wrong
      sentences in the guide, not a systemic metadata failure.
- [ ] **Map the three codes client-side, or decide not to.** Cheap, independent of the backend
      answer, and it removes a raw code from the user's screen. `OP-SIG-ARITY-MISMATCH` belongs in
      `compute-status.ts` and `ExplainSection.tsx`; the `AC-LABELS-*` pair belongs on the atom
      write path, not the compute surface. Weigh against EPIC-260082 finding 19's lesson: these
      maps are best-effort and can never be certified complete.
- [ ] **Should the adoption checklist grow a probe step?** ICR-260081 already adopted "diff the
      guide alongside the schema" after 9.3.0's behavioural change went unnoticed. That rule would
      still not have caught this, because the guide and the metadata were *both* read and simply
      disagree. The rule that would have caught it is "run the probes against the new bundle".
