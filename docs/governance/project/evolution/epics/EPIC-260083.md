# EPIC-260083: Operation arity contract — MINUS loses an operand on edit

- Epic ID: EPIC-260083
- Title: Operation arity contract — MINUS loses an operand on edit
- Persona/Actor: Any user who opens an existing computed atom in the Compute tab's formula
  builder. No category or COLLECT involvement — this is the arithmetic path.
- Value statement: For a user editing a computed atom, deliver a formula builder that cannot
  silently discard part of their formula, so that opening an atom to change one thing does not
  quietly change another.
- Context: Inspector → **Compute** tab → *Edit formula*, on an atom whose operation is
  `MINUS` with more than two arguments.
- Problem statement: **The builder silently truncates a valid formula and writes the truncation
  back.** `BUILTIN_OPERATIONS` (`src/features/workspace-compute/operation-metadata.ts:36`)
  declares `MINUS: { min: 2, max: 2 }`. `fitRows` in `FormulaBuilder.tsx` trims rows above `max`
  **in the `useState` initializer**, i.e. on mount, before the user touches anything. So for an
  atom stored as `MINUS(a, b, c)`:
  1. the builder renders two slots — `c` is gone from the UI with no notice;
  2. `save()` writes `rows.map(r => r.value)`, i.e. `args: [a, b]`;
  3. the atom's value changes, and nothing ever told the user.

  **The server accepts far more than two.** Verified 2026-09-01 against a live 9.3.0 backend with
  `tools/backend_probe/probes/operation_arity.py`: three constants `10, 3, 2` evaluate to **`5.0`**
  and eight evaluate to **`0.0`**, both `evaluationStatus: success` — so MINUS folds left to right
  and `discoverOperations`' `MINUS minArity=2 maxArity=null` (unbounded) is accurate.

  The client's `max: 2` came from the guide, which is **wrong**: `user-guide.md:1243` says MINUS
  takes "exactly two atom UUID references or constant keys". EPIC-260069 had no reason to doubt
  it — `discoverOperations` published no arity metadata before 9.3.0.
- Expected outcome: A formula the server accepts survives a round-trip through the builder
  unchanged. Opening and saving an atom without editing it is a no-op on the payload.
- Success metric(s): a stored `MINUS` with three or more arguments renders every argument in the
  builder and re-saves byte-identically; a regression test pins the round-trip and fails against
  today's `max: 2`.
- Non-goals:
  - Fixing the backend contract contradiction — that is EPIC-260084.
  - Consuming `minArity`/`maxArity` from `discoverOperations` to replace the client table. That
    is EPIC-260082's recorded registry follow-up, and EPIC-260084 shows the published metadata is
    not yet trustworthy enough to read. This epic changes one wrong constant, not the mechanism.
  - Any change to COLLECT, the category queries, or the constants gate.
- Constraints: the backend pin is `~9.3.0`. Whatever value replaces `max: 2` must be justified by
  something better than the guide's prose, since the guide is what caused this.
- Dependencies: EPIC-260069 (the builder and the arity table this corrects). **Not blocked by
  EPIC-260084:** the bound no longer needs the backend's ruling, because MINUS's real behaviour is
  measured (unbounded, left-fold) rather than read off either disputed source.
- Risks/assumptions:
  - **Truncation-on-mount is verified by reading, not by running.** The evaluation
    (`MINUS(10,3,2) = 5.0`) is measured; the `fitRows` consequence is derived from the code path
    and has NOT been reproduced in the UI. Reproduce it first — this project's standing lesson is
    that a derived consequence is not a verified one.
  - **Frequency measured 2026-09-01: zero.** The builder cannot author a >2-arg MINUS (that is the
    bug's mirror image), so an affected atom must come from the API, an import, or another client —
    and `operation_census.py` found none among the demo account's 25 atoms. **Severity high,
    frequency zero here**, which is why this is parked rather than urgent. One account on one
    server bounds the observation, not the exposure.
  - **Confirmed, not assumed:** `SUM/4 → 16.0` and `PRODUCT/4 → 60.0` agree with the client, and
    `DIVIDE` really is exactly-two. MINUS is the only operation whose client cap is tighter than
    reality — the only direction that loses data.
- Target window: **Parked 2026-09-01** — not a priority. Resume at the single open ideation bullet (read-preserving vs. authoring scope); the other four are closed by measurement.
- Validation approach: a unit test that mounts `FormulaBuilder` on a stored `MINUS(a,b,c)` and
  asserts three slots render and an untouched save emits three args — verified to fail against
  `max: 2`. Ideally an e2e round-trip through `updateAtom`.

## Ideation Bullets

Four of the five resolved by measurement on 2026-09-01 (`tools/backend_probe`, live 9.3.0). One
genuine decision remains, and it is a scope call, not a fact.

- [x] **MINUS's real maximum: unbounded.** `operation_arity.py --op MINUS --args 8` evaluates to
      `0.0` and `maxArity` is `null`, so eight is not a ceiling either — there is no bound to pin.
      The client should say `max: undefined` (variadic), which is what `SUM` and `PRODUCT` already
      say and what both were re-measured to be (`SUM/4 → 16.0`, `PRODUCT/4 → 60.0`).
- [x] **Semantics: left-fold subtraction, measured.** `MINUS(10,3,2,1,1,1,1,1) = 0.0` — that is
      `((((((10-3)-2)-1)-1)-1)-1)-1`, so arguments subtract left to right in payload order. The
      guide documents none of this (`user-guide.md:1243` still says "exactly two"), which is
      EPIC-260084's problem, not this epic's. **What remains is UI copy**, and only if the fix
      offers authoring — see the open bullet below.
- [ ] **OPEN — Fix scope: read-preserving, or authoring too?** The two differ in size and risk.
      - *Read-preserving* (minimal): stop `fitRows` discarding args that already exist, so a stored
        `MINUS(a,b,c)` renders and re-saves intact. Does not let anyone create one. Small, and it
        closes the data-loss path entirely.
      - *Authoring*: additionally let a user add a third slot, which needs copy explaining
        left-to-right order — a user who reads `MINUS` as "subtract the second from the first"
        has no reason to expect a third to keep subtracting.
      They can ship separately and in that order. **This is the decision that sizes the epic.**
- [x] **Blast radius: LATENT, not active.** `operation_census.py` walked all 25 atoms the demo
      account owns: 4 carry an operation — `COLLECT/1arg ×2`, `SUM/1arg ×1`, `SUM/2arg ×1`. There
      is no `MINUS` atom at all, so nothing is currently damaged. Bounds what was observed, not the
      blast radius: one account, one server. Anyone who authored a `MINUS` through the API rather
      than the builder is still exposed.
- [x] **Nowhere else.** `discover_operations.py` reports exactly two client/server disagreements,
      `MINUS` and `DIVIDE`, and only one of them truncates: the client caps `DIVIDE` at 2 and the
      server really does reject a third (`OP-SIG-ARITY-MISMATCH`), so that cap is correct and the
      published metadata is the wrong half (EPIC-260084). `SUM` and `PRODUCT` agree. **MINUS is the
      only operation whose client cap is tighter than reality, which is the only direction that
      loses data.**
