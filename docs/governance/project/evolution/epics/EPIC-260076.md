# Epic: EPIC-260076 — Hierarchical Category Dimensions

- Epic ID: EPIC-260076
- Title: Hierarchical Category Dimensions — nest, re-parent, and browse a dimension tree
- Persona/Actor: Knowledge worker modelling their own taxonomy.
- Value statement: For users organizing what data exists, deliver a nestable dimension hierarchy so a taxonomy can express `Region ▸ Country` rather than a flat list of unrelated dimensions.
- Context: EPIC-260068 shipped the Categories navigator with dimensions as a **flat** top level. Users modelling real taxonomies immediately reach for nesting (a dimension under a dimension), find no affordance for it, and misread the per-node editor's "add value" form as dimension creation.
- Problem statement: The backend has supported the dimension hierarchy since schema 9.2.0 — `createCategoryDimension(parentDimensionKeys, childDimensionKeys)`, `connectCategoryDimensions`, `disconnectCategoryDimensions`, and `CategoryDimensionOutput.parentDimensionKeys`. The frontend fetches `parentDimensionKeys` and **discards it**, sends no parent on create, and wires no connect/disconnect. The capability is entirely unexposed, and the UI actively misleads: the only "key + Display name" form under a dimension creates a *value*.
- Expected outcome: Dimensions render as a tree (roots + nested children). A dimension can be created under a parent, and an existing dimension can be re-parented or detached back to a root. Nesting is expressed from the child (to place B under A, edit B); the schema's parent-side `childDimensionKeys` wiring is not exposed, since it would be a second control for the same capability. Server-enforced taxonomy rules (single parent, no cycles, value/dimension alignment) surface as readable messages rather than raw `CAT-*` codes.
- Success metric(s): A user builds a two-level dimension tree with values under each level without leaving the rail, and can correct a mis-parented dimension without deleting and recreating it.
- Non-goals: Multi-parent dimensions (backend is single-parent for v1 — `CAT-MULTIPLE-PARENTS-UNSUPPORTED`); taxonomy sharing/transfer UI (grants exist in schema; a future epic, mirroring EPIC-260074); any backend change (none is required); drag-and-drop re-parenting unless ideation concludes it is proportionate.
- Constraints: No interface change — the contract already supports every operation needed, so no ICR applies. The dimension tree must be assembled client-side: `retrieveCategoryBrowse(dimensionKey)` returns a dimension's **root values**, not its child dimensions, so hierarchy comes from `retrieveCategoryDimensions` + `parentDimensionKeys`. Edit affordances stay gated on the node's real `accessLevel` (ADR-260064 §5, unchanged), except the move affordance, which requires OWNER — re-parenting is owner-only server-side (ADR-260071 §6). Parent candidates are unfiltered: read access suffices on a parent.
- Dependencies: EPIC-260068 (navigator, `category-operations.ts`, `CategoryTree`, permission gating). Picks up the drag-to-reparent follow-up EPIC-260068 recorded as deferred.
- Risks/assumptions: Dimension nesting and value containment are validated **independently**. `connect`/`disconnectCategoryDimensions` check only that the dimension exists, that it gains no second parent (`CAT-MULTIPLE-PARENTS-UNSUPPORTED`), and that no cycle forms (`CAT-DIMENSION-CYCLE`) — values are never consulted. `CAT-VALUE-PARENT-DIMENSION-MISMATCH` is reachable only from value operations. A value with no parent value is the normal root case, and is what `retrieveCategoryBrowse(dimensionKey)` returns as its top-level entry points. The real risk is narrower: re-parenting an **already-populated** dimension does not revalidate existing `UNDER_CATVAL` edges, so a value can retain a parent that is no longer in the immediate parent dimension — stale data surfacing under the wrong drill-down path, never a blocked call. First-time builds are unaffected.
- Target window: TBD. (Epic status lives only in `epic-index.md`.)
- Validation approach: Unit tests for the dimension-tree builder (roots, nesting, cycle-safety) and error mapping; E2E for create-under-parent, re-parent, detach, and a refused attach mid-move. The two `CAT-*` mappings stay unit-level: the UI prevents provoking either, so an E2E path would have to mock a server the user cannot reach.

## Ideation Bullets

Resolved 2026-07-21 with the project owner. Guiding principle for this epic: **ship the smallest
thing that makes nesting usable, test it in the product, improve from what that reveals.** Several
bullets are therefore closed as deliberate v1 exclusions rather than as decisions.

- [x] **Nesting populated dimensions — resolved, no work.** Nest first, pair values whenever you like. Dimension nesting does not inspect values and cannot return `CAT-VALUE-PARENT-DIMENSION-MISMATCH`; unpaired values are the normal root case and filter atoms normally. This is already the server behavior — nothing to decide, nothing to build. (Recorded because an earlier reading of this epic wrongly generalized the value-connect rule to the dimension-connect call and treated it as a blocker.)
- [x] **Stale value edges after re-parenting a populated dimension — excluded from v1.** Re-parenting does not revalidate existing `UNDER_CATVAL` edges, so a value can retain a parent outside the immediate parent dimension and surface under the wrong drill-down path. No detection, warning, or cleanup is built. It affects only re-parenting of already-populated dimensions, never a first-time build, and is recoverable through the existing value editor. Revisit once real use shows whether it occurs in practice. → follow-up, not a task.
- [x] **Re-parenting affordance — form-based, with two-call move semantics.** A parent selector in `CategoryNodeEditor` expressed from the child (edit B to place it under A). Attaching a *root* dimension is a single `connectCategoryDimensions` call. **Moving an already-parented dimension is not** — connecting over an existing parent returns `CAT-MULTIPLE-PARENTS-UNSUPPORTED`, so a move is `disconnect` then `connect`: two calls, not atomic. v1 exposes this as one "Set parent" action that issues both and reports honestly if it lands halfway (the dimension is left a root). "Detach to root" is included — re-parenting is untestable without being able to undo a mistake. Drag-and-drop stays out: EPIC-260068 judged it disproportionate and nothing has changed.
- [x] **Create-with-parent — yes, atomically.** `AddDimensionForm` gains an optional parent selector passed as `parentDimensionKeys` on `createCategoryDimension`. Avoids a transient orphan and makes the common case (build a tree top-down) one step.
- [x] **Facet scoping across the hierarchy — no change in v1.** Filter semantics stay exactly as ADR-260064 shipped: OR within a dimension, AND across dimensions, `includeDescendants` on the value axis only. A nested dimension is still filtered independently; selecting a parent dimension does **not** implicitly pull in child dimensions' values. Extending `includeDescendants` to the dimension axis is a distinct feature with its own semantics and would change behavior users already rely on. → follow-up.
- [x] **Tree assembly and lazy loading.** The dimension tree is built client-side from `retrieveCategoryDimensions` + `parentDimensionKeys` — `retrieveCategoryBrowse(dimensionKey)` returns a dimension's root *values*, never its child dimensions. Per-node lazy value loading is unchanged; a nested dimension loads its values on expand exactly as a root one does.
- [x] **Error surfacing — map the two dimension codes.** `CAT-MULTIPLE-PARENTS-UNSUPPORTED` and `CAT-DIMENSION-CYCLE` get readable, user-facing messages. (Refined during implementation: the UI makes neither reachable in a single session — cycle targets are filtered out and a move always disconnects first — so the mappings are defense in depth against races and stale data. ADR-260071 §4 carries the accurate rationale.) `CAT-VALUE-PARENT-DIMENSION-MISMATCH` is a value-operation error, unreachable from dimension nesting, and stays on the generic path.
- [x] **`CategoryNodeEditor` disambiguation — in this epic.** The editor's three unheaded forms (two containing a "Display name" field, and an add-child form whose placeholders match the add-dimension form) are what made the taxonomy UI unreadable in the first place. The epic reworks that component to add the parent selector, so the headings land in the same task rather than a separate change.
- [x] **Existing flat dimensions — no migration.** They become roots and are corrected with the same re-parenting control. Nothing special is needed.
- [x] **Full code + test coverage task** — included as T6.

## Deferred follow-ups (not tasks)

- Editor-wide success feedback. The rail is `CategoryNodeEditor`'s feedback surface for all four
  actions; delete closes the editor and add-value clears its inputs for functional reasons, not as
  confirmations. Read as "two confirm, two don't", a later pass would add messages to rename and
  set-parent — a second channel for outcomes the rail already shows. Preserve the rule, not the
  apparent inconsistency. (Recorded in the component's doc comment too.)

- Stale `UNDER_CATVAL` edges after re-parenting a populated dimension — no detection or cleanup in v1.
- `includeDescendants` on the dimension axis (selecting a parent dimension pulling in child dimensions' values).
- Drag-and-drop re-parenting — inherited from EPIC-260068's deferral, still judged disproportionate.

**Resolved during implementation (was an open question):** re-parenting requires **OWNER** on the
dimension being moved — a bare `OWNS` edge, so an EDITOR grant is not enough — and only **read** on
the target parent (backend team, 2026-07-21). The move form is gated on OWNER independently of
`canEditNode`; parent candidates correctly stay unfiltered, since read suffices and the server
returns only readable dimensions. Answered by asking, not inferred (LRN-002). See ADR-260071 §6.

## Learnings

- **Verify capability against the authoritative schema, not the client's documents.** This epic was
  nearly opened as an ICR plus backend work on the strength of a missing argument in
  `src/api-contract/` — a client selection, not the contract. `docs/crystord_server/schema.graphql`
  had supported the hierarchy all along. Captured as LRN-002.
- **Ask about authorization; do not infer it.** The schema annotates `owner-only` where it means it
  and was silent on `connect`/`disconnectCategoryDimensions`. The backend team's answer — OWNER on
  the dimension being moved, read on the target parent — contradicted the natural reading of "edit
  rights" and changed the gate. An inferred answer would have shipped an affordance that fails for
  every EDITOR grant, and `shareCategoryDimension` already issues those.
- **An API constraint the UI hides still needs a state.** A move is `disconnect` then `connect`
  because the server refuses a second parent. That is two non-atomic calls, so "the move failed" and
  "the move succeeded but the refresh failed" are different outcomes; conflating them told the user
  the exact inverse of the server state.
- **Identity that is namespaced server-side must stay namespaced client-side.** Dimension keys and
  value keys are separate namespaces; keying tree nodes on the raw key let a value silently
  overwrite a dimension, pruning it and its subtree from the parent selectors.
- **Adversarial review aimed inside the implementation misses record-vs-code drift.** Five review
  lenses found four defects, all in code. An independent human pass found three more, two of which
  were records claiming behaviour that was never built. Two further defects surfaced only in a third
  pass, after the epic had twice been declared complete — nine in total, and the ones found last
  were not the least severe.
