# EPIC-260080: In-App Help — surface end-user documentation inside the workspace shell

- Epic ID: EPIC-260080
- Title: In-App Help — surface end-user documentation inside the workspace shell
- Persona/Actor: Crystord workspace users (new and existing) trying to learn the interface
  without leaving the app — not developers integrating against the GraphQL API directly.
- Value statement: For a user unfamiliar with a concept or a view, deliver in-app help reachable
  in one click so they can learn the interface without leaving the app or asking someone else.
- Context: Any time a user is in the workspace and isn't sure what a concept (Atom, Label, Bond,
  Category/Dimension/Value, Formula, Grant) means or how to work a specific surface. The shipped
  surfaces, read from the slot registries rather than from memory (2026-09-01), are four center
  views — **Network, Flow, Table, Board** — five inspector tabs — **Details, Classify, Compute,
  History, Share** — and two left-rail navigators — **Labels, Categories**. Today the only recourse
  is trial-and-error or asking someone else.
- Problem statement: The workspace shell shipped ten feature epics (EPIC-260066 through
  EPIC-260075, plus EPIC-260077) with no in-product explanation of what things mean or how to use
  them. Documentation for this audience **has never existed**. `docs/user-guide.md` is not a stale
  or superseded version of it — it is the backend behavior contract, written for developers
  building against the GraphQL API, and it stays exactly that (see Non-goals). The two documents
  serve different readers and can both be correct at once; the gap this epic fills is that the
  non-developer reader has nothing at all.
- Expected outcome: A discoverable help entry point in the workspace shell opens a navigable,
  task-oriented guide covering the app's core concepts and its per-surface usage, without the user
  losing their place in the current workspace.
- Success metric(s): help is reachable in **one click** from anywhere in the shell (this metric is
  load-bearing — it is what resolves bullet 1); content covers at least the core concepts and every
  registered center view, inspector tab and navigator; closing help returns the user to exactly the
  state they left (no lost selection, scroll position, or workspace context).
- Non-goals: not a rewrite, replacement, or correction of `docs/user-guide.md` — that remains the
  developer/API reference and is not in scope; no video or tutorial media in v1; no per-field inline
  tooltips/coach-marks in v1 (plausible future epic); no help-usage analytics in v1; no in-panel
  search in v1 (bullet 6); no contextual help keyed to the inspector tab or navigator lens in v1
  (bullet 5 — the open question this epic records rather than answers).
- Constraints (per EPIC-260082's adopted process change, **each of these gets a test named after it**
  at implementation time):
  - C1 — the help entry point is a single control in the shell header, placed **before**
    `AccountMenu` so the `Account menu` accessible name stays rightmost; five e2e specs use it as
    their authenticated sentinel.
  - C2 — the entry point carries an explicit accessible name. Every other icon-only control in this
    header has one (`SearchBar.tsx:110`, `FacetChips.tsx:55`, `BetaBanner.tsx:34`); an unlabelled
    glyph would breach the a11y floor held since ADR-260031.
  - C3 — opening or closing help unmounts nothing in the workspace subtree.
  - C4 — help renders `descriptor.label` for every surface heading and never restates a UI label as
    a string literal, so a rename propagates by construction.
  - C5 — help content is typed TypeScript, not markdown, and is co-located in the feature module
    that owns the surface it describes.
  - C6 — every registered view, inspector tab and navigator has a help section, enforced at compile
    time (see bullet 8).
  - **Correction to the pre-ideation draft of this section, recorded because the original was
    factually wrong and would have misled the plan review:** the earlier text said this epic "must
    not casually introduce a second, competing header control without reconciling with ADR-260066's
    deliberate consolidation into one avatar menu." Measured against `WorkspaceShell.tsx:113-125`,
    the header already holds four children — the `Crystord` title, a full `SearchBar` (which itself
    contributes a submit button, a clear button, one button per label chip and one per recommended
    label), `FacetChips` (one button per active filter), and `AccountMenu`. A help button is roughly
    the fifth to eighth interactive element, not the second. ADR-260066's binding Decision is scoped
    to the top-right **account cluster** (ThemeToggle, Account, Sign Out), not to the header as a
    whole; "the header stops accumulating loose buttons" is a Consequence, not a rule; and the only
    machine-enforced residue is `architecture.test.ts:3012-3015`, which asserts `AccountMenu` present
    and `ThemeToggle` absent. Two further inherited inaccuracies are corrected here: no **avatar**
    ships (`AccountMenu.tsx:132-142` renders a text button showing the username, falling back to the
    literal `'Account'`), and `PreferencesPanel` is a **centered modal**, not the "slide-in
    panel/drawer" the draft named twice.
- Dependencies: EPIC-260066 (Foundation — the slot/registry architecture this hooks into, and the
  source of `slot-types.ts`); EPIC-260070 / ADR-260066 (the header-consolidation precedent this
  reconciles with); EPIC-260077 (most recent shell-level UI addition and its review rigor, and the
  precedent for declining a REQ-FR); ADR-260031 (a11y floor); ADR-260072 (the Flow arrow-direction
  inversion that motivates bullet 8's honesty clause).
- Risks/assumptions: Split into two measurable statements, because the pre-ideation draft priced
  both halves of "contextual help" at the expensive one. (a) **Center-view contextual help is in
  v1** — `activeView` is already shell state (`WorkspaceShell.tsx:36`) in the same scope the panel
  renders. (b) **Inspector-tab and navigator-lens contextual help is the genuine open scope
  question** — `activeTabId` (`Inspector.tsx:23`) and `activeLensId` (`LeftRail.tsx:25`) are
  component-local and absent from `WorkspaceContextValue`, so reaching them means either changing a
  documented shell contract with three consumers or adding a second entry point. Also assumed:
  content can be authored by the team without a dedicated technical-writing pass. The residual risk
  this epic **cannot** close is semantic drift — see the honesty clause in bullet 8.
- Target window: TBD.
- Validation approach: unit coverage of the panel (dialog role, `aria-modal`, accessible name,
  close by button/backdrop/Escape, focus restore) and of the entry point's reachability from every
  shell state; contextual open tested as a pure function from `activeView` to section id; a compile-
  time gate that every registered surface has a help section; and a human content-accuracy review at
  both the Ready and Done gates. Content accuracy is explicitly **not** a coverage claim.

## Ideation Bullets — Resolved (2026-09-01, plan review; approved by the project owner this date)

- [x] **Entry point: a standalone `?` button in the header, placed before `AccountMenu`.** Rejected:
  an item inside `AccountMenu`. The decisive argument is this epic's own success metric — help
  "reachable in one click from anywhere in the shell" — which a menu item fails at two clicks; the
  choice was already settled by the metric before taste entered. Nothing is violated: see the
  Constraints correction above. Cost asymmetry confirms it — a sixth menu item churns
  `AccountMenu.test.tsx:110-111` (which pins the exact five-item label array) and `:180` (which pins
  the roving-tabindex array), while a standalone button touches neither. And this project has twice
  decided the same tradeoff toward the visible control: ADR-260046:10 named discoverability as
  defect #1 of the double-click-to-create gesture, and ADR-260031:46 rejected removing the legend on
  discoverability grounds. Not `both` — two entry points to one panel is the over-provisioning this
  repo consistently rejects (ADR-260066:50, ADR-260066:56, EPIC-260077:64-67).
- [x] **Presentation: the existing centered-modal panel, not a route.** Three independent reasons,
  any one sufficient. ADR-260066:54 already rejected "routing settings pages instead of modals" for
  this class of surface, so a route reopens an Accepted decision. There is no router to route with —
  it was removed in commit `7443cb2`; `react-router` remains in `package.json` (pinned there by
  `architecture.test.ts:318-320`) but nothing mounts it, and `AuthGuard.tsx` is dead code kept alive
  only by two string-matching assertions. And the panel satisfies this epic's state-preservation
  metric **by construction** while a route breaks it by construction: panels mount as siblings of
  the workspace tree (`WorkspaceShell.tsx:168-202`), so `selectedAtomId`, `activeView`,
  `categoryFacets`, the search state, the working set, the Inspector's tab and React Flow's node
  positions all survive with zero new code — whereas unmounting the shell empties a working set that
  only repopulates on an explicit search.
- [x] **Content structure: a short concepts section first, then one section per registered surface,
  keyed by registry id.** The navigation-mirroring and concepts-first drafts each independently
  concluded they needed the other half — the former had no home for Atom/Label/Bond, the latter
  needed a closing "where each concept lives on screen" map. Keying surface sections to registry ids
  rather than to hand-written headings is what makes bullet 8's compile-time gate possible, so this
  bullet and bullet 8 are one decision.
- [x] **Content source: hand-authored, with `docs/user-guide.md` used for concepts only.** Measured:
  the guide is 1546 lines, of which ~7.6% is even a candidate for reuse and roughly 1% (L21-36,
  "Why The Product Uses Atoms") is liftable verbatim. This is not a criticism of the guide — it is
  an API contract document doing its job for its own reader. But its prose is written in backend
  vocabulary (`properties.shellies`, `properties.nuclearies`, `operation`) that reaches no
  user-visible label in `src/`, and it describes classification from the API's perspective (L95:
  assign Values, dimension derived) where the UI makes the user choose the dimension first
  (`CategoriesSection.tsx`). Lifting that text would import the wrong vocabulary and the wrong
  mental model into user-facing help.
- [x] **Content lives in typed TypeScript modules, co-located in the owning feature module.**
  Rejected: markdown files, and content inlined in the panel component. No markdown renderer is a
  dependency (8 runtime deps, none transitively), so markdown means a new dependency for static
  prose; inlining is a `react-refresh/only-export-components` lint error; and — decisively — if
  content lands in `.md`, bullet 8's compile-time gate cannot exist and the only available instrument
  is the `toContain` grep that EPIC-260078 documented going silently vacuous. Co-location
  (`src/features/workspace-compute/help.ts` rather than a central content directory) is what makes
  bullet 8's process gate function: the help diff then lands in the same directory a reviewer is
  already reading. This also keeps each content module inside the ≤200-line guideline that one
  central file would blow.
- [x] **Static vs contextual: v1 opens to the active center view's section.** Neither the static
  panel the draft proposed nor full contextual help. The draft treated this as one indivisible scope
  call and priced both halves at the expensive one; they are two calls at very different prices (see
  Risks (a) and (b)). View-contextual is nearly free because `activeView` is already shell state in
  the scope the panel renders. Inspector-tab and lens contextual help is recorded as the open
  question rather than attempted, because lifting `activeTabId`/`activeLensId` into
  `WorkspaceContextValue` changes a documented shell contract with three consumers — the speculative
  structure this project has repeatedly declined.
- [x] **In-panel navigation: a table of contents with anchors. No search in v1.** At an estimated
  ~2,000 words across roughly nine sections, search would be built for a scale that does not exist —
  the same speculative-structure objection that rejected the top-bar slot registry (ADR-260066:50).
  Revisit if content grows materially.
- [x] **Coverage: one task, scoped as a deliverable rather than a percentage.** New help modules at
  100% line+branch (held by review, as ADR-260060 has it, not by a CI gate); `WorkspaceShell.tsx`
  keeps its existing EPIC-260066 T9 documented exemption. Testable and tested: entry-point presence
  and keyboard reachability from every shell state; open/close by button, backdrop and Escape;
  `role="dialog"`, `aria-modal` and accessible name; focus-into and focus-restore (largely inherited
  from `use-modal-focus.ts`); contextual open as a pure function from `activeView` to section id;
  and every registered surface having a non-empty help body, asserted over **imported registry
  data**. Explicitly **not** a coverage claim: whether the prose is true. That is a human review at
  both gates, and the record says so rather than letting a percentage imply otherwise.
- [x] **Added during ideation — freshness gate: a compile-time presence gate, plus a named ceiling.**
  Make `help: HelpSection` a **required field** on the three slot descriptors in `slot-types.ts`;
  registering a surface without one then fails typecheck (`TS2741`, probe-verified against
  TypeScript 6.0.2). Add one runtime test importing `views`/`inspectorTabs`/`navigators` and
  asserting each `help.body` is non-empty — an assertion over imported data, which no doc comment
  can satisfy, so it does not inherit the failure mode EPIC-260078 recorded. Do **not** add a
  `toContain` assertion against help prose; that is the `architecture.test.ts:1267-1290` shape and it
  will read as coverage while providing none.
  **The ceiling, stated plainly because it would otherwise read as solved.** The measured risk is
  not the one the draft implied. The registries have not changed since 2026-07-18 (45 days), only
  five commits have touched `src/` since 2026-07-24, and nothing in the live queue adds a surface —
  so "a new view ships without help" has a currently-empty trigger set. What does move is meaning
  inside a frozen surface: `1d08b63` (2026-08-26, ADR-260072) inverted the direction an arrow means
  in the Flow view in 21 lines, and `82ae3ed` rewrote the Compute tab across 19 files
  (+2,207/−103) while `inspector-registry.ts` stayed byte-identical. This gate is green through both.
  It proves presence, not truth. The only instrument for semantic drift is the process gate in T7,
  which is a human check that will sometimes be skipped — there is no compiler for "this sentence is
  still true," and this epic does not claim one.
- [x] **Added during ideation — governance records: a T1 ADR, and no REQ-FR.** The ADR covers the
  epic (entry point, panel surface, registry-keyed content model, freshness gate), following the
  house pattern in which twelve consecutive feature/shell epics each shipped one. Rejected: a
  placement-only ADR scoped to a single control's position, which would be a first in this repo and
  breaks the one-ADR-per-epic-T1 convention. No REQ-FR: the pre-ideation premise that every shipped
  feature epic carries one is **false** — `requirement-index.md:115-124` maps ten requirements to ten
  epics, and three shipped epics have none, including EPIC-260077, which declined on the grounds that
  client-local shell state is not a requirement-taxonomy-worthy external contract. In-app help is the
  same shape.
