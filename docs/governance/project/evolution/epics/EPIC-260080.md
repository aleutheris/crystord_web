# EPIC-260080: In-App Help — surface end-user documentation inside the workspace shell

- Epic ID: EPIC-260080
- Title: In-App Help — surface end-user documentation inside the workspace shell
- Persona/Actor: Crystord workspace users (new and existing) trying to learn the interface
  without leaving the app — not developers integrating against the GraphQL API directly.
- Value statement: For a user unfamiliar with a concept or a view, deliver in-app help reachable
  in one click so they can learn the interface without leaving the app or asking someone else.
- Context: Any time a user is in the workspace and isn't sure what a concept (Atom, Label, Bond,
  Category/Dimension) means or how to work a specific view (Table, Board, Graph, Flow, Classify,
  Compute, History, Share). Today the only recourse is trial-and-error or asking someone who has
  read `docs/user-guide.md` — and that guide assumes GraphQL, not the rendered UI.
- Problem statement: The workspace shell shipped ten feature epics (EPIC-260066 through
  EPIC-260075, plus EPIC-260077) with no in-product explanation of what things mean or how to use
  them. The one written guide that exists, `docs/user-guide.md`, is a GraphQL/API reference for
  developers — it isn't reachable from the UI and doesn't teach screen navigation.
- Expected outcome: A discoverable help entry point in the workspace shell opens a navigable,
  task-oriented guide covering the app's core concepts and its per-view usage, without the user
  losing their place in the current workspace.
- Success metric(s): help is reachable in one click from anywhere in the shell; content covers at
  least the four core concepts (Atom/Label/Bond/Category) and every current center view and
  navigator; closing help returns the user to exactly the state they left (no lost selection,
  scroll position, or workspace context).
- Non-goals: not a rewrite or replacement of `docs/user-guide.md` (that stays the developer/API
  reference); no video or tutorial media in v1; no per-field inline tooltips/coach-marks in v1
  (plausible future epic, not this one); no help-usage analytics in v1 unless ideation decides
  otherwise.
- Constraints: must not casually introduce a second, competing header control without reconciling
  with ADR-260066's deliberate consolidation into one avatar menu; should follow the existing
  panel/drawer convention already in `ui-shell` (`PreferencesPanel.tsx`) unless ideation finds a
  clear reason not to; content must stay accurate to the currently shipped feature set or it will
  mislead rather than help.
- Dependencies: EPIC-260066 (Foundation — App Shell; the slot/registry architecture this hooks
  into); EPIC-260070 (Account & Settings — avatar menu & settings surface; ADR-260066 is the
  header-consolidation precedent this must reconcile with); EPIC-260077 (Resizable Left Rail;
  most recent precedent for a shell-level UI addition and its review rigor).
- Risks/assumptions: Assumes a single, mostly-static help panel is sufficient for v1 rather than
  per-view contextual help — if ideation finds users need "help for the view I'm on right now,"
  that's a scope question to resolve, not a reason to block. Assumes content can be authored by
  the team without a dedicated technical-writing pass.
- Target window: TBD.
- Validation approach: e2e coverage that the help entry point opens from every shell state and
  that closing it restores prior focus/scroll/selection state; content reviewed against the
  actual shipped view set at the Ready gate (so it can't go stale before it ships).

## Ideation Bullets

- [ ] **Entry-point placement.** A standalone "?" icon next to `AccountMenu` (more discoverable,
  but reintroduces a second header control after ADR-260066 deliberately consolidated to one) vs.
  a new item inside `AccountMenu` (stays consistent with that consolidation, one click deeper).
  This touches the exact header region ADR-260066 governs, so the decision likely needs its own
  short ADR rather than a drive-by choice.
- [ ] **Presentation pattern.** Reuse the existing slide-in panel convention
  (`PreferencesPanel.tsx`) so the user never leaves workspace context, vs. a dedicated route/page.
  Leaning panel-for-consistency; confirm there's no reason (e.g. content length) that argues
  against it.
- [ ] **Content structure.** Organize around the app's actual navigation (`GraphViewTabs`:
  Table/Board/Graph/Flow; Inspector tabs: Classify/Compute/History/Share; Categories/Labels
  navigators) rather than by backend concept, so what a user finds matches what's on their screen.
  Needs an agreed table of contents before any content is written.
- [ ] **Content source and scope.** `docs/user-guide.md`'s "Core Concepts" / "A Simple Mental
  Model" sections (Atom, Labels, Bonds, Categories) are conceptually reusable, but the file as a
  whole is a GraphQL reference, not a UI walkthrough. Decide whether new content is hand-authored,
  adapted from those sections, or both — and where it actually lives (standalone doc vs. content
  embedded directly in the panel component).
- [ ] **Static vs. contextual.** Single always-the-same panel for v1, or does opening help from
  inside a specific view (e.g. while on the Compute tab) jump to that view's section? Decide the
  v1 bar; contextual jump-to-section is a reasonable stretch goal but shouldn't block v1 if it
  adds significant complexity.
- [ ] **In-panel navigation at scale.** With content length still unknown, decide whether v1 needs
  in-panel search/filter or whether a short table of contents with anchor links is enough at
  launch size.
- [ ] **Coverage task shape.** Per `epic-process.md`, confirm what "coverage" means here given the
  deliverable is mostly static content plus one new interactive entry point — likely entry-point
  reachability, keyboard, and a11y tests matter more than the content itself, which isn't code.
