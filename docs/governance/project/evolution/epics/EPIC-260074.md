# Epic: EPIC-260074 — Share Inspector tab: atom-level access grants

- Epic ID: EPIC-260074
- Title: Share Inspector tab — atom-level access grants
- Persona/Actor: Any user controlling who can see/edit their atoms.
- Value statement: For users controlling access, deliver per-atom sharing so they can grant and revoke who can view or edit an atom.
- Context: The backend supports atom-level sharing (`shareAtom` / grants / roles, `revokeAtomAccess`, `listAtomGrants`) — a branding pillar ("Control") — invisible in the UI. Read-side access gating already exists (BI-260061).
- Problem statement: There is no sharing/access surface; users cannot manage who has access to an atom.
- Expected outcome: An Inspector **Share** tab — view current grants and grant/revoke access by principal (username or workspace key), principal type, and access level.
- Success metric(s): Users share an atom with a principal at a chosen level and see/revoke who has access.
- Non-goals: Account/workspace settings (EPIC-260070); taxonomy permissions (future extension mirroring this model, per Q2); live collaboration (async only); ownership transfer (`transferAtomOwnership` exists — deferred, destructive-handoff UX deserves its own slice).
- Constraints: Async sharing (no RTC, per REQ-CR-260010); consistent with the existing access-control gating (BI-260061).
- Dependencies: EPIC-260066 (inspector-tab registry).
- Target window: TBD. (Epic status lives only in `epic-index.md`.)
- Validation approach: Unit tests for grant/revoke flows + access-level display; E2E sharing an atom and confirming the grant.

## Ideation Bullets — Resolved (2026-07-17, plan review; approvals batch-delegated by the project owner this date)

- [x] **Grant/role UI.** Grants list from `listAtomGrants` (principalName · principalType · level · grantedAt) with per-row revoke (inline two-step confirm). Grant form: principal text input (username for USER, workspace key for WORKSPACE — the backend resolves; `CR-16-PRINCIPAL-UNKNOWN` already in the central mapper), principal-type select, level select (`EDITOR`/`VIEWER` — the grantable `AccessLevel`, deliberately distinct from `EffectiveAccessLevel`). Mutations refetch the grants list; feedback via the established `AccountActions`-style pending/feedback pattern.
- [x] **Consistency with BI-260061 gating.** Listing and mutating grants are **owner-only** in the schema, so the Share tab registers with `when: (atom) => atom.accessLevel === 'OWNER'` — non-owners never see a tab that can only error. The tab also states the atom's current effective level for orientation.
- [x] **Taxonomy-permission reuse seam (Q2).** The grant list/form components are built presentational (grants + callbacks in, no atom-specific coupling in the rendering layer) inside the feature, so a future taxonomy-sharing epic can lift them; they are **not** promoted to ui-primitives now (single consumer — same rule that kept the atom-ref picker in EPIC-260069).
- [x] **Module shape.** New api-contract `sharing-operations.ts` (LIST_ATOM_GRANTS_QUERY, SHARE_ATOM_MUTATION, REVOKE_ATOM_ACCESS_MUTATION, `AtomGrant` + grantable `AccessLevel` types); new feature `workspace-share` (ShareTab), registered as inspector tab `share`.
- [x] **Full code + test coverage task** — included (T5).
