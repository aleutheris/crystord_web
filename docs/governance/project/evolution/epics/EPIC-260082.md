# EPIC-260082: Category-based COLLECT — collect atoms by category dimension and value

- Epic ID: EPIC-260082
- Title: Category-based COLLECT — collect atoms by category dimension and value
- Persona/Actor: Crystord users who classify atoms with category dimensions/values (the taxonomy
  built via EPIC-260067 / EPIC-260068 / EPIC-260076) and want computed atoms driven by that
  taxonomy rather than by labels.
- Value statement: For a user who has invested in a category taxonomy, deliver COLLECT queries
  that filter by dimension and value — including whole subtrees — so a computed atom can roll up
  "everything under Region → Europe" without shadowing that taxonomy as labels.
- Context: In the Inspector **Compute** tab, when picking `COLLECT` as the operation. Today the
  query picker offers exactly one registered query, `atoms_with_labels`, so the only way to
  collect by category is to mirror every category value with a parallel label — which the user
  must then maintain by hand on every atom, in two places that silently drift apart.
- Problem statement: EPIC-260069 shipped COLLECT deliberately label-only, recording the reason as
  "backend not built" (EPIC-260069 §Non-goals; ADR-260065 §3). **That reason is now stale.**
  Backend schema 9.3.0 — pinned by ICR-260081 on 2026-08-29 — registers two category COLLECT
  queries (`docs/user-guide.md:1316-1318`):
  - `atoms_in_category_value` — atoms categorized at *exactly* `value_key` in `dimension_key`;
    descendant-only assignments excluded.
  - `atoms_in_category_subtree` — atoms at `value_key` **or any descendant value**, deduplicated.
  - Both require the string constants `dimension_key` and `value_key`; a pair that does not
    resolve in the caller's own taxonomy yields an **empty list, not an error**.

  The frontend consumes neither: `COLLECT_QUERY_SPECS` in
  `src/features/workspace-compute/operation-metadata.ts` is a hand-written one-entry table listing
  only `atoms_with_labels`.
- Expected outcome: A user picking COLLECT can choose a category-based query and select its
  dimension and value from dropdowns — never by typing a raw key — and the builder refuses to save
  a query whose required constants are empty. The exact-vs-subtree distinction is presented as two
  plainly-worded choices.
- Success metric(s): a user builds a working `atoms_in_category_subtree` atom without typing JSON
  or a raw `dimension_key`/`value_key`; a COLLECT with an empty required constant cannot be saved;
  the existing `atoms_with_labels` path — including its empty-labels refusal — behaves exactly as
  before.
- Non-goals (all deliberately deferred; this epic is a minimal, extendable slice):
  - **Combined labels + category COLLECT.** Not deliverable here at any effort: COLLECT takes
    "exactly one argument — the name of a registered query" (`user-guide.md:1303`), all three
    registered queries are single-axis, and no list-intersection operation exists to compose two
    COLLECTs. A combined filter requires the backend to register a fourth query in
    `collect_queries.json` — a separate ICR conversation with the backend team, not frontend work.
    (Note the asymmetry for whoever picks that up: `retrieve(labels:, categories:)` *does* accept
    both axes, and EPIC-260068's facet scoping already uses them together — search can combine
    axes, COLLECT cannot.)
  - **Live `collectQueries` registry.** `collectQueries: [CollectQueryInfo!]!`
    (`schema.graphql:21`) publishes the registry with each constant's `type`/`minItems`, which
    would remove the hand-maintained table that caused this gap and make future server-side
    registrations appear without a frontend release. Deferred deliberately: consuming it widens
    the frontend's used surface inside the pinned schema, raising the ICR question this epic
    otherwise avoids entirely. Strongest follow-up candidate.
  - `ConstantSpec`-driven validation; the shared `CategoryTree` pick-mode picker in place of
    dropdowns; promoting a shared taxonomy hook (that belongs with EPIC-260078's duplication
    theme); exact-vs-subtree as a single entry plus a toggle.
  - Unchanged from EPIC-260069: charts/analytics (REQ-CR-260010), the manual-vs-computed hard
    fork, the Explain section, Flow badges.
- Constraints: the backend pin is `~9.3.0` (ICR-260081) — this epic must not require a version
  above it. **No cross-feature import:** `architecture.test.ts:35-51` forbids
  `workspace-compute` importing Classify's `useTaxonomy`, so the dimension/value data comes from a
  local hook over the shared `api-contract/category-operations` documents. The category queries
  only resolve values the caller owns, so offering an unownable value would silently produce an
  empty collection. `<= 200` lines per file still applies.
- Dependencies: EPIC-260069 (the formula builder this extends); EPIC-260067 / EPIC-260068 (the
  taxonomy being filtered on); EPIC-260076 (hierarchical dimensions — the reason
  `atoms_in_category_subtree` is worth having); ICR-260081 (the 9.3.0 pin); REQ-FR-260073 (the
  compute requirement whose acceptance criteria this amends).
- Risks/assumptions:
  - ~~Assumes the two category queries behave as documented against a live 9.3.0 server —
    verified against the schema and user guide only, **not** against a running backend.~~
    **RETIRED 2026-09-01:** measured against a live 9.3.0 server with `tools/backend_probe`.
    Both queries resolve, the exact-vs-subtree distinction is real, the registry matches the
    client's hand-copied table exactly, and all three `OP-COLLECT-*` codes fire as documented.
    See §Backend Verification.
  - **Knowingly-accepted debt:** the local taxonomy hook duplicates logic Classify's
    `useTaxonomy` already has. The architecture rule forbids sharing it directly, and promoting it
    is out of scope here. This is the same copy-paste pattern EPIC-260078 exists to address —
    recorded as a decision, not an accident.
  - The empty-labels refusal guards a defect that already reached the field once (REQ-FR-260073
    change log, 2026-07-23; LRN-003). Refactoring the constants path is exactly how it regresses.
    **Corrected 2026-08-31 (round 5):** that field defect is no longer reproducible — 9.3.0 closed
    it at the source (`user-guide.md:1305`, granting LRN-003 §7's unfiled ask). The refusal is
    retained because saving an atom certain to fail evaluation is still worth preventing, not
    because it averts a collect-everything result.
- Target window: TBD.
- Validation approach: e2e that a category COLLECT is built end-to-end from the Compute tab and
  persists through `updateAtom`; unit coverage of the generic required-constants gate across all
  three queries; an explicit regression test that `atoms_with_labels` still refuses an empty
  `labels` list.

## Ideation Bullets

All resolved 2026-08-31 under a deliberate minimal-slice scope. The owner passed the `Ready`
plan-review gate on 2026-08-31; implementation of T1–T6 may begin (`epic-process.md` §Epic States).

- [x] **ICR needed? No.** v1 consumes only queries already in `api-contract`
  (`RETRIEVE_CATEGORY_DIMENSIONS_QUERY` / `RETRIEVE_CATEGORY_VALUES_QUERY`, both already used by
  Classify) and adds no new backend field to any selection set. The used surface does not widen,
  so the drift ICR-260081 §3 flagged does not recur here. Deferring `collectQueries` is what buys
  this — if that follow-up is ever pulled back in, the ICR question returns with it.
- [x] **Registry: keep the client-side table.** Add the two category queries to
  `COLLECT_QUERY_SPECS` rather than fetching `collectQueries`. Live registry deferred (see
  Non-goals) precisely because it reintroduces the ICR question.
- [x] **Generalize the constants gate.** Replace `requiresLabels: boolean` with a per-query list
  of required constant keys, and gate save on one generic non-empty check over that list. The
  label case and both category cases then fall out of the same few lines. ~~**Record the rationale
  difference:** an empty `labels` list is vacuously true server-side and collects *every* atom the
  caller owns (ADR-260027 D2); an unresolvable category pair returns *nothing*.~~
  **CORRECTED 2026-08-31 (review round 5) — the struck text was false against the pinned
  contract.** 9.3.0 rejects empty required constants outright (`user-guide.md:1305`), so both
  families fail loudly and identically; the gate is kept but its hazard is one hazard, not two. The
  D2 reasoning belongs to the SEARCH path only. See §Implementation Notes finding 8. Left visible
  rather than rewritten: this bullet is the record of what was decided, and the correction is part
  of the trail.
- [x] **Dimension/value input: two dependent dropdowns**, fed by a local hook over the shared
  `api-contract` category documents (dimensions on mount, values lazily per selected dimension).
  Not the shared `CategoryTree` pick-mode widget — dropdowns are the smaller honest bar, and raw
  text inputs are rejected outright because a typo yields a silently empty collection, not an
  error.
- [x] **Stale keys: sticky option, not a marker.** When a stored `dimension_key`/`value_key` is
  absent from the loaded list (renamed, deleted, or authored against another taxonomy), append it
  to the dropdown as the selected option showing the raw key. Without this a `<select>` with no
  matching option renders blank-or-first while state still holds the stale key — the user sees one
  value and saves another. Do not block save. Consistent with the existing shortened-UUID fallback
  for out-of-set atom references (ADR-260065 §3).
- [x] **Exact vs. subtree: two entries, plainly worded** (at this value / and everything beneath
  it). No single-entry-plus-toggle mapping layer — it would break the moment the registry gains a
  query nobody has written copy for.
- [x] **Free-text "Other" query: leave untouched — zero diff.** The `OTHER_QUERY` sentinel
  (`FormulaBuilder.tsx:24`) keeps its labels editor and its ungated save. Removing it would cost
  code *and* drop a capability; it is also the escape hatch that lets a user reach a future
  server-registered query (including a combined labels+category one) with no frontend release.
- [x] **Requirement: amend REQ-FR-260073 in place, no new REQ.** Mandatory, not optional — its
  criteria at lines 37 and 46-47 are label-specific ("COLLECT's labels constant edits via the
  shared label chip editor", "renders the collected labels") and become false for category
  queries. The record already carries a Change Log with a 2026-07-23 amendment precedent.
- [x] **ADR-260065: no action needed.** `artifact-model.md:54` gives ADRs no "amended" state —
  `Accepted` transitions only to `Superseded by <id>`. But ADR-260065 §3 wrote the decision
  conditionally ("label-only **until** the backend adds category collect"); the condition is now
  met, so this epic *fulfils* the ADR rather than reversing it. Nothing to supersede. Recorded
  here so it is not re-litigated.
- [x] **Coverage bar.** 100% line+branch on the new hook (a ~40-line module; the standing
  new-module precedent is trivially achievable at that size); new and changed behaviour covered in
  the modified files; and the `atoms_with_labels` empty-labels regression test is a hard floor,
  not a nice-to-have.

## Implementation Notes (T1–T6, 2026-08-31 — per-task review complete; all six Done 2026-09-01)

**Modules.** Beyond the planned changes, three small modules were extracted rather than growing
`FormulaBuilder.tsx` past the 200-line guideline: `collect-constants.ts` (what a COLLECT save
writes + the generic gate), `use-collect-draft.ts` (the six interdependent COLLECT state atoms and
their transitions), and `category-option-list.ts` (the pure sticky-option helper — eslint's
`react-refresh/only-export-components` forbids exporting it beside a component). `FormulaBuilder.tsx`
ended at 160 lines, down from 198 before the epic.

**Two defects found by adversarial review and fixed** — both invisible to the green suite, both in
the "UI shows one thing, state holds another" class this epic was already guarding against:

1. **Stale label draft survived an editor swap.** `LabelChipEditor` keeps its input in its *own*
   state and reports changes only while mounted. Typing a label without pressing Enter, switching to
   a category query, and switching back left `FormulaBuilder` holding the draft while the remounted
   editor showed an empty box — so the save was enabled, wrongly satisfied the empty-labels gate, and
   would have written a label the user could no longer see. Fixed by dropping the draft only on an
   actual editor swap, which leaves the ADR-260027 D2 rule (an uncommitted draft counts while the
   editor is on screen) intact. Regression test verified to fail without the fix.
2. **Category constants leaked into the generic constants editor.** Converting a category COLLECT to
   SUM surfaced `dimension_key`/`value_key` as hand-editable rows and wrote them as SUM constants —
   asymmetric with `labels`, which has always been filtered out. Fixed by making the exclusion
   symmetric via `COLLECT_OWNED_CONSTANTS`.

Also fixed: a stale "Could not load categories." notice persisted above a picker that had since
loaded fine; a successful values load now clears it.

**Known limitation, deliberately not fixed:** a values load that fails is cached as empty and never
retried for that dimension (the alternative is a retry/backoff path this minimal slice does not
warrant). The dimension picker still works and the error is surfaced.

**Follow-up spotted during review, correctly out of scope here:** `countInputArgs`
(`formula-format.ts`) counts a COLLECT's query-name argument as an input, so "Explain this value"
reads *"computed from 1 input"* for every COLLECT regardless of what it collects. Identical before
and after this epic — a pre-existing defect in EPIC-260069's surface, not a regression, and fixing
it here would have widened the epic beyond its minimal slice.

**Second review round (2026-08-31, owner).** Five further findings, all accepted and fixed; none
was a blocker. The two substantive ones were coupled, so they were fixed together:

1. **The sticky option asserted a falsehood while loading.** `optionsWithSelected` annotated
   "(not in your taxonomy)" whenever a key was absent from the list — but an empty list also means
   *still loading* or *load failed*. It therefore libelled the user's own valid data on **every**
   open of a saved category COLLECT, for the duration of the fetch — the same "UI shows one thing,
   the truth is another" class the sticky option exists to prevent. It now takes an `authoritative`
   flag and shows the bare key, unannotated, until the list is known to be complete.
2. **A successful values load cleared a still-true dimensions error** (introduced by the first
   round's own fix). `dimensionsError` and `valuesError` are now tracked separately, which also
   gives finding 1 a *per-list* authority signal — a values-only failure must not suppress a
   legitimate annotation on the dimension picker, which loaded fine.
3. Two exported `CollectDraft` types in one folder — the input shape is now `CollectConstantsInput`.
4. The `CollectEditor` type collided with the `CollectEditor` component, forcing an import alias;
   the type is named `CollectEditorKind` at source and the alias is gone.
5. `stringConstant` was defined twice — `formula-format.ts` now uses the shared one; stray blank
   lines from the refactor removed.

Also corrected here: the first round's claim that "every file" was under the 200-line guideline was
**wrong** — it held for source files, but `FormulaBuilder.test.tsx` is 411 lines. Consistent with how
the repo already treats test files, but the claim as written overstated it.

**Third review round (2026-08-31, owner).** One finding, the most serious of the whole epic and the
only one that could lose user data:

6. **The `COLLECT_OWNED_CONSTANTS` reservation was global, not scoped to COLLECT atoms.** Round 1's
   fix for the COLLECT→SUM leak filtered `labels`/`dimension_key`/`value_key` out of the generic
   constants editor *unconditionally* — it never checked whether the atom arrived as a COLLECT. A
   plain SUM carrying a hand-authored constant named `value_key` therefore had it stripped from the
   editor; any argument referencing it then dangled, blocking the save with **"A constant argument
   references a key that no longer exists"** — naming a key that does exist and is invisible. With
   no such argument the failure was quieter and worse: the constant was silently dropped on save.
   These are plausible user-authored names in a taxonomy-heavy product, so the reservation is now
   scoped by `collectInitially` (`initial` is fixed for the life of the mount).
   **This also fixes a pre-existing bug this epic inherited:** `labels` was reserved unconditionally
   before the epic too, so a SUM carrying a `labels` constant had the same defect. Both cases are
   now pinned by tests, each verified to fail without the fix.

**Fourth review round (2026-08-31, owner).** One finding — the epic's own Constraints line, written
and then not implemented:

7. **The value picker offered values the COLLECT queries cannot resolve.** `retrieveCategoryValues`
   is access-scoped to taxonomy the caller owns **or has been granted** (`user-guide.md:270-272`,
   each output carrying the caller's `accessLevel` per `1099-1101`), but the category COLLECT
   queries "only resolve values you own" (`user-guide.md:1320`). The implementation bridged the two
   without filtering, so a **granted** value selected cleanly, satisfied the required-constants
   gate, saved without error — and then collected nothing while reporting success. Reachable
   through ordinary use, not a corner case: assignments are limited to *readable* taxonomy
   (`user-guide.md:1102-1104`), so a user can classify atoms at a shared value, see those
   assignments in Classify, and then build a COLLECT on that value.

   This is `EPIC-260082:59-61` verbatim — the constraint was recorded and never implemented — and
   it reintroduced through a different door the exact silent-empty outcome that justified choosing
   dropdowns over a text box.

   Fixed asymmetrically, which is the only correct shape: **values** are marked and disabled when
   `accessLevel !== 'OWNER'` and the save is blocked with a stated reason; **dimensions stay
   unfiltered**, because the dimension is matched by key and a granted dimension is legitimately
   usable (`user-guide.md:1320`). Marked rather than hidden, so the "why isn't the value I can see
   in Classify offered here?" question is answered in place. Uses `accessLevel`, already in the
   selection set — no contract surface, no ICR — following the `CategoryNodeEditor.tsx:61`
   precedent. Structural consequence: the taxonomy fetch moved into `useCollectDraft` (still lazy,
   `enabled` only for category queries) so the gate lives with the save, and
   `CategoryConstantSelects` went back to presentational.

**Process change adopted from this round.** Four of the eight defects were *written constraints that
never became code*, and 100% coverage caught none of them — the tests encoded the same assumptions
as the implementation, so they executed every line while verifying the wrong thing. Going forward on
this project: **every bullet in an epic's Constraints section gets a test named after it, written at
implementation time.** Coverage measures which lines ran, not whether the constraints hold; only a
constraint-derived test does that.

**Fifth review round (2026-08-31, owner).** One finding, and the most consequential for the record
rather than the code:

8. **The epic hardened a rationale the contract it pins explicitly denies.** `user-guide.md:1305` —
   rewritten by commit `7d0b6de`, the 9.3.0 adoption — states that an empty required constant fails
   evaluation (`OP-COLLECT-CONSTANTS-INVALID`), "no query runs and no rows are returned — an empty
   filter never means 'match everything'". That is exactly the backend ask LRN-003 §7 had recorded
   as *identified but not yet filed*; 9.3.0 granted it, along with LRN-003's second ask
   (`collectQueries` / `ConstantSpec` / `minItems`). **So the "empty labels collects every atom you
   own" hazard was fixed at the source in the very release this epic exists to consume** — and the
   epic, not noticing, re-entrenched the obsolete claim in four places, including user-facing copy
   and a *ratified acceptance criterion* that told future readers not to reconcile it.

   The asymmetry the epic insisted on is real but **inverted** from what was written:

   | Path | 9.3.0 behaviour |
   | --- | --- |
   | Empty `labels` | `OP-COLLECT-CONSTANTS-INVALID` — fails **loudly**, no rows |
   | Unowned/unresolvable category pair | constants are non-empty strings, so validation passes; query runs, returns empty — **succeeds silently** |

   The gate is kept (blocking beats shipping an atom certain to fail evaluation) and ADR-260027 D2
   is untouched — on the SEARCH path an empty label set genuinely does mean "all atoms"; only the
   transplant onto COLLECT was wrong. Corrected in `operation-metadata.ts`, `collect-constants.ts`
   (both messages + copy), REQ-FR-260073 (criterion + change-log entry), LRN-003 (§7 asks recorded
   as granted, §8 follow-on lesson), and ICR-260081 (retrospective note).

   **This promotes finding 7:** with the labels path now failing loudly, the unowned-value path is
   the only silently-wrong COLLECT left — the epic's gate was protecting the path the backend had
   already made safe.

**Second process change adopted.** ICR-260081 §4 called 9.3.0 "purely additive" — accurate about the
GraphQL schema, and exactly why this was missed: constants-validation semantics live only in
`user-guide.md`, where no schema diff can see them. **An ICR adopting a new backend bundle must diff
the guide alongside the schema, and re-check any client-side rationale that asserts backend
behaviour.** Recorded in ICR-260081 and LRN-003 §8.

**Sixth round — systematic backend-assumption sweep (2026-08-31).** A read-only audit of **137
backend-behaviour claims** across `workspace-compute` and the compute parts of `api-contract`,
each checked against the pinned 9.3.0 schema + guide. Five findings, all fixed:

9.  **The round-5 correction was incomplete, and had been reported as complete.** Four surviving
    sites of the retracted "empty labels collects every atom" claim: `use-collect-draft.ts:77`,
    `operation-metadata.test.ts:59` and `:61`, and a test *name* at `FormulaBuilder.test.tsx:202`.
    Root cause worth keeping: the round-5 verification grepped for remembered phrasings
    (`"collect every atom you own"`, `"vacuously true"`) and could not match `"every owned atom"`
    or `which COLLECT reads as "every atom"`. **Grepping for remembered wording is not
    verification.**
10. **`discoverOperations` exposes NO arity metadata — false since 9.3.0**, and load-bearing.
    `OperationFunction` publishes `minArity`/`maxArity`/`numericOnly` (`schema.graphql:80-84`) —
    LRN-003 §7's second ask, also granted. Consequence, now recorded in code: an operation the
    server registers but the client table omits falls to `argBounds`'s `{ min: 0 }`, so the builder
    will save `args: []` for an operation whose real `minArity` is higher, and `numericOnly` is
    never enforced. **Deliberately not closed by consuming the fields** — that widens the used
    surface and reopens the ICR question this epic defers; the fallback stays permissive rather
    than guessing a minimum the server already publishes. Same false premise corrected at
    `operation-metadata.test.ts:15` and `api-contract/compute-operations.ts:4`.
11. **The taxonomy pickers silently truncated at 25.** `user-guide.md:1096` — "Pagination defaults
    to `limit=25`, `max limit=100`" — and neither query passed a limit. A dimension with 26 values
    showed 25, and a stored `value_key` beyond the page rendered **"(not in your taxonomy)"**: the
    round-1 defect, reintroduced through a door opened while fixing it. Now requests the documented
    maximum **and forfeits authority over a full page**, since nothing in the response distinguishes
    "exactly 100" from "the first 100 of more". (Pre-existing project-wide: `use-taxonomy.ts` passes
    no limit either — out of scope here, worth its own pass.)
12. **The three `OP-COLLECT-*` codes 9.3.0 added were unmapped** on both explanation surfaces, so a
    failed COLLECT showed a generic sentence plus a raw code — for the very feature this epic
    shipped. Sharpest via the free-text query path the epic deliberately leaves ungated, which makes
    `OP-COLLECT-QUERY-UNKNOWN` reachable from the UI. Added to `ExplainSection` and `compute-status`.
    **Round nine amends this (finding 19): three of FOUR unmapped evaluation codes.** Scoping the
    sweep to "what 9.3.0 added" is what stopped it short — the fourth predates 9.3.0.
13. `OperationFunction.description` was typed non-null; the schema says `String`. Now `string | null`.

**Seventh review round (2026-08-31, owner).** Two findings, both follow-ons from earlier rounds'
own fixes rather than from the original implementation:

14. **The page ceiling was silent.** Finding 11 raised the request to the documented maximum and
    stopped the false "(not in your taxonomy)" claim on a full page — but it left the ceiling
    itself invisible. 100 is a **hard server cap** (`user-guide.md:1096`: over-limit raises
    `OR-QUERY-LIMIT-EXCEEDED`, so asking for more returns no more) and the pickers do not page, so
    a dimension with more values than that presents its first page as the whole taxonomy. Editing
    a saved atom is safe — the sticky option keeps a stored value visible and, since finding 11,
    unannotated — but **authoring is simply blocked**: the value cannot be reached and nothing says
    why. Not exotic for a taxonomy-heavy product in this market: a `Gemeente` dimension is 342
    values, `Country` ~195. `dimensionsTruncated`/`valuesTruncated` are now reported alongside the
    authority flags and rendered under the affected `<select>` as *"Showing the first 100 …; some
    are not listed."* Deliberately a **separate** signal from `*Authoritative`: that flag only
    suppresses a false claim, and suppressing a claim is not the same as making a true one.
    **Follow-up, not taken here:** offset paging (`CategoryValueSelector.offset` already exists —
    no contract surface) or a typeahead picker. The control question should be settled first — a
    342-option `<select>` is the wrong widget whether or not it is paged.
15. **The new ownership gate had a load window.** Finding 7's `valueUnusable` check is
    data-dependent, and mid-load the data is absent: the value list is empty, so a stored
    `value_key` falls to `optionsWithSelected`'s sticky branch, which builds a bare
    `{key, displayName}` carrying **no `unusable` flag** — `isUnusableValue` returns false and the
    save is enabled. Clicking Save inside that window writes an unownable value straight past the
    gate. Narrow: fresh authoring cannot reach it, since selecting an unowned value requires the
    loaded list where the option renders `disabled`. But it defeats the gate in precisely the case
    the gate exists for — re-opening an atom that already collects nothing to find out why. The
    save is now blocked while the category editor's taxonomy is loading, ordered **after** the
    missing-constants check so a fresh formula still gets the useful instruction instead of a
    spinner message. Costs nothing in practice: an unset value is already blocked, so the clause
    only bites while a **stored** one is being verified. The guard checks `editor === 'category'`
    explicitly rather than leaning on the hook's `enabled` invariant, and the test mock ignores
    `enabled` on purpose so a regression there fails the suite.

**Eighth review round (2026-08-31, adversarial fan-out over round seven's own fixes).** Five
reviewer lenses, each finding independently refuted by a separate agent; three survived. Two are
defects in round seven's fixes — the round that introduced them also introduced their bugs, which
is the point of reviewing a fix rather than trusting it.

16. **The page-ceiling notice asserted what the response cannot establish.** Completeness is
    `length < PAGE_LIMIT`, so a taxonomy of **exactly 100** values reads as incomplete and the note
    claimed *"some are not listed"* under a picker showing the entire dimension. The hook already
    concedes the ambiguity in the comment above the same computation — a full page "may have more
    behind it, and nothing in the response says which" — and treats it **conservatively** for
    `*Authoritative` while treating it as **certain** for the note. Same signal, two opposite
    readings. Fixed by hedging the copy to *"Showing the first 100 …; there may be more."*, which
    is true in both cases, and by correcting the `*Truncated` docstring, which had inherited the
    same overstatement ("the server had to cut it off"). The alternative — resolving the ambiguity
    with a probe read at `offset=100, limit=1` — is available (`offset` is already on both
    selectors) and remains the better long-term answer if paging is ever added. This is finding 14
    committing the exact error finding 14 was written to prevent: stating as fact something the
    data cannot support.
17. **The load-window gate closes one of three holes, not three.** Finding 15 gates on
    `categoriesLoading`, but loading is only one of the ways the value list can lack access data;
    a **failed** values load and a **ceiling-full** page both leave `loading === false` with the
    stored key on the unflagged sticky option, so `valueUnusable` reads false and the save is
    released with the value never verified. Unlike the loading window, those states never resolve
    within the mount (`requestedRef` dedupes, so there is no retry). **Deliberately left open**,
    with the gap now written into the code at the gate: the obvious fix — gating on
    `valuesAuthoritative` — would permanently strand any stored value past the page ceiling,
    contradicting the recorded "an unresolvable stored key does not block save" decision. Severity
    is genuinely low and that is why it can wait: no *new* unownable value is reachable (unusable
    options render `disabled`, and changing dimension clears the value), so the only save these
    states permit is a byte-identical re-save of already-stored constants with "Could not load
    categories." on screen. What is lost is the ownership diagnostic, in the one state that never
    clears. Needs a design call on "unknown vs unusable", not a wider boolean.
18. **`*Authoritative` keys on the current error MESSAGE, not on whether that list loaded** — a
    pre-existing defect from round two's error split, reproduced by running the hook. `valuesError`
    is a single scalar that any later success clears, while the empty-on-failure cache entry is
    per-dimension: load A (fails), pick B (succeeds, clearing the error), pick A again — `requestedRef`
    blocks a refetch, so `valuesAuthoritative` is now **true** over the empty list from the failure,
    with no error, no loading note, and no retry path short of reopening the editor. Violates the
    flag's own documented contract ("loaded, and not failed"). ~~**Open** — not round seven's to
    fix, and the honest fix is per-list load *outcome* rather than a shared error string.~~
    **CLOSED in round nine (2026-09-01)** by exactly that fix — see finding 20.

The epic's largest recorded risk — that every backend behaviour it encodes was read from prose and

**Confirmed through the UI (2026-09-01, owner).** A category COLLECT authored by hand in the
Compute tab — dimension and value picked from the dropdowns against live taxonomy — stored content
**byte-identical to the probe's, same 11 refs in the same order**. That closes the one gap the
probes structurally could not reach: the probes speak raw HTTP with hand-written documents, the app
speaks Apollo (`cache-first`, normalized cache) with its own selection sets, and the two agreeing
exactly means the whole path is sound — dropdown population, the emitted payload, evaluation,
storage, and display. The two halves were built to be independent precisely so that their agreement
would mean something.

**Not exercised:** the demo account owns all of its taxonomy (12 values, all `OWNER`), so the
ownership gate itself is still unobserved in the field. Testing it needs a value shared from a
second account. Note this is the *safe* direction: with every value `OWNER`, `markUnusableValues`
marks nothing and the gate is inert, so it cannot produce a false block in a single-user workspace —
it only ever adds a refusal, never a permission.

**Two backend contract defects found, both OUTSIDE this epic** (recorded here only so they are not
lost — neither is EPIC-260082's to fix, and neither is a regression it introduced):

- **`MINUS` is variadic on the server, and the client silently truncates it.** `MINUS(n0,n1,n2)`
  over constants `10,3,2` evaluates to **5.0**. `user-guide.md:1243` says "exactly two"; it is
  wrong. `BUILTIN_OPERATIONS` sided with the guide (`{min: 2, max: 2}`), so `fitRows` trims to two
  slots **on mount** — opening an existing three-argument MINUS drops the third operand from the UI
  and saving writes the truncated formula back. Silent data loss on edit, pre-existing since
  EPIC-260069.
- **`discoverOperations.maxArity` is not trustworthy.** It reports `null` (unbounded) for `DIVIDE`,
  but `DIVIDE(n0,n1,n2)` is rejected with `OP-SIG-ARITY-MISMATCH`. So the guide is right about
  DIVIDE and the metadata is wrong; the metadata is right about MINUS and the guide is wrong. Each
  half of the backend contract is wrong about a different operation. **This bears directly on the
  recorded follow-up to consume the live registry** — reading `maxArity` today would import a false
  bound for DIVIDE.

**Three undocumented error codes** observed, none in `user-guide.md` and none mapped in the client:
`OP-SIG-ARITY-MISMATCH` (evaluation), `AC-LABELS-EMPTY` and `AC-LABELS-INVALID` (write-time — an
atom cannot be created with no labels, and a label must match `[A-Za-z_][A-Za-z0-9_]{0,127}`).
Finding 19's point stands and is now measured twice over: the guide is not an exhaustive code list.

**Third process change adopted.** A sweep scoped to *"what did the new bundle add"* cannot find a
gap that predates the bundle (finding 19). Pair it with the inverse question — *what does the
governing ADR require this surface to handle, and does it?* — because that is the question that
would have caught this one in EPIC-260069.
