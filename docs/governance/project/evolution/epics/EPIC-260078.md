# EPIC-260078: Shared Persisted-Preference Helper — Deduplicate `use-preferences.ts`

- Epic ID: EPIC-260078
- Title: Shared Persisted-Preference Helper — Deduplicate `use-preferences.ts`
- Persona/Actor: Maintainers extending `WorkspacePreferences` (adding, fixing, or reading any
  localStorage-backed shell preference)
- Value statement: For a maintainer touching any workspace preference, deliver one shared
  read/write/try-catch helper so a bug fixed once is fixed everywhere, instead of hand-fixing the
  same shape in N near-identical copies.
- Context: `use-preferences.ts` now hand-copies the same triplet — a localStorage key constant, a
  `read<Name>()` function (try/getItem/parse/validate/catch/fallback), and a `useEffect` that
  persists on change — five times (`homeEmphasis`, `computeBadges`, `leftRailCollapsed`,
  `rightRailCollapsed`, `leftRailWidth`). EPIC-260077's post-implementation review (2026-08-27)
  found and fixed three real bugs in the newest copy (`leftRailWidth`) that stemmed directly from
  this duplication: an unclamped fallback-to-default path, an empty string parsing as a valid `0`,
  and a viewport-cap formula that had to be manually kept in sync across two call sites instead of
  reading one shared source.
- Problem statement: The pattern isn't a hypothetical future need — it already has five live
  instances and a demonstrated bug-per-copy track record. Each new preference (or bugfix to an
  existing one) risks re-introducing a variant of the same class of bug instead of inheriting a
  fix made once.
- Expected outcome: A single generic helper (shape TBD by ideation) that every current preference
  is migrated onto, with byte-for-byte-identical externally observable behavior — same
  `WorkspacePreferences` public shape, same localStorage keys, same sticky-default-on-first-render
  semantics, same try/catch-swallow-on-unavailable behavior.
- Success metric(s): all five preferences migrated; `use-preferences.ts` net line count drops;
  100% of existing `use-preferences.test.tsx` assertions keep passing unmodified (behavior-
  preserving refactor, not a rewrite); at least one new unit test proves a bug class this
  duplication caused (e.g. empty-string handling) cannot regress in any preference going forward.
- Non-goals: no change to what any preference does, is called, or is keyed as in localStorage; no
  new preferences added by this epic; no change to `WorkspacePreferences`'s public interface.
- Constraints: This is an internal-implementation refactor of an already-Done, already-shipped
  module (ADR-260061 / EPIC-260066) — no public API/interface changes, so no ICR is expected, but
  every existing consumer (`Inspector`, `PreferencesPanel`, `LeftRail`, and their tests) must keep
  working unmodified, since none of them should need to know this refactor happened.
- Dependencies: EPIC-260066 (`use-preferences.ts` origin, ADR-260061); EPIC-260077 / ADR-260073
  (source of the `leftRailWidth` copy that prompted this).
- Risks/assumptions: Assumes a single generic shape can cover all five preferences' actual
  differences (boolean vs. string-literal vs. numeric-with-extra-clamp values) without leaking
  complexity back into each call site — if ideation finds it can't cleanly cover `leftRailWidth`'s
  extra clamp step, that's a bullet to resolve, not a reason to abandon the other four.
- Target window: TBD — not urgent; no open bug is currently caused by this, only closed ones.
- Validation approach: full existing `use-preferences.test.tsx` suite (and every other suite that
  exercises `WorkspacePreferences`) must pass unmodified after the refactor; a new test targeting
  the empty-string-parses-as-valid-number bug class, written once against the shared helper so it
  covers every preference, not just `leftRailWidth`.

## Ideation Bullets

- [ ] **Helper shape.** Decide the generic signature — most likely something like
  `usePersistedState<T>(key: string, read: () => T, serialize: (value: T) => string)` returning
  `[T, (value: T) => void]`, called once per preference with each preference's own parse/validate/
  clamp logic passed in — versus a narrower `usePersistedString`/`usePersistedBoolean`/
  `usePersistedNumber` trio matching the three value shapes actually in use. Trade generality
  against how much each preference's own quirks (e.g. `leftRailWidth`'s clamp) still need to live
  at the call site either way.
- [ ] **Migration order and blast radius.** Migrate one preference at a time (smallest first,
  e.g. `rightRailCollapsed`) with the full test suite green after each, or all five in one pass?
  Given this touches code from four separate Done epics, prefer the safer incremental path unless
  there's a clear reason not to.
- [ ] **Where the helper lives.** Stays private to `use-preferences.ts` (only one current
  consumer module), or gets promoted to a shared location (e.g. `ui-shell/` internal utils) if a
  second localStorage-backed hook already exists elsewhere in the codebase — check before deciding
  rather than assuming.
- [ ] **Coverage task.** Confirm the dedicated coverage task (epic-process.md requirement) targets
  the *new* shared helper's own edge cases (unavailable localStorage, malformed stored value,
  empty string) directly, so coverage isn't just "the same five preference tests happen to still
  pass" — it should be possible to see the bug class ADR-260077's review found is now guarded once,
  not five times.
