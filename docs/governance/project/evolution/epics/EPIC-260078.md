# EPIC-260078: Shared Persisted-Preference Helper — Deduplicate `use-preferences.ts`

- Epic ID: EPIC-260078
- Title: Shared Persisted-Preference Helper — Deduplicate `use-preferences.ts`
- Persona/Actor: Maintainers extending `WorkspacePreferences` (adding, fixing, or reading any
  localStorage-backed shell preference)
- Value statement: For a maintainer touching any workspace preference, deliver one shared
  read/write/try-catch helper so a bug fixed once is fixed everywhere, instead of hand-fixing the
  same shape in N near-identical copies.
- Context: `use-preferences.ts` hand-copies the same triplet — a localStorage key constant, a
  `read<Name>()` function (try/getItem/parse/validate/catch/fallback), and a `useEffect` that
  persists on change — five times (`homeEmphasis`, `computeBadges`, `leftRailCollapsed`,
  `rightRailCollapsed`, `leftRailWidth`). A src-wide sweep during ideation (2026-09-01) raised the
  true count to **six**: `src/styles/ThemeProvider.tsx:23-50` is a sixth instance of the identical
  React-state-backed shape, and is the acknowledged template the preferences file was modeled on
  (`use-preferences.ts:9`). EPIC-260077's post-implementation review (2026-08-27) found and fixed
  three real bugs in the newest copy (`leftRailWidth`) that stemmed directly from this duplication:
  an unclamped fallback-to-default path, an empty string parsing as a valid `0`, and a viewport-cap
  formula that had to be manually kept in sync across two call sites instead of reading one shared
  source. Ideation surfaced a fourth, still latent, in the two boolean readers (see the FINDING
  paragraph below the ideation bullets).
- Problem statement: The pattern isn't a hypothetical future need — it already has six live
  instances and a demonstrated bug-per-copy track record. Each new preference (or bugfix to an
  existing one) risks re-introducing a variant of the same class of bug instead of inheriting a
  fix made once.
- Expected outcome: A single generic helper that every current preference is migrated onto, with
  externally observable behavior preserved — same `WorkspacePreferences` public shape, same
  localStorage keys, same sticky-default-on-first-render semantics, same
  try/catch-swallow-on-unavailable behavior. The one deliberate semantic change is the boolean
  missing-key/`DEFAULT_*` mismatch, which is unobservable today (bullet 5).
- Success metric(s): all five preferences plus `ThemeProvider` migrated; `use-preferences.ts` net
  line count drops from a **counted** 186 (measured 2026-09-01) to a **counted** figure recorded at
  close-out — not an estimate (EPIC-260082 §"Correcting this record's own arithmetic"); all 21
  existing `use-preferences.test.tsx` assertions keep passing with the file byte-identical
  (measured baseline: 21/21 green, 2026-09-01); one named test per bug class this duplication
  caused, each verified to fail without its fix.
- Non-goals: no change to what any preference does, is called, or is keyed as in localStorage; no
  new preferences added by this epic; no change to `WorkspacePreferences`'s public interface;
  `src/api-contract/auth-token.ts` is **not** migrated (different lifecycle — module-level sync seed
  at import time for the Apollo auth link, imperative event-driven writes, an explicit `removeItem`,
  no React state); `src/features/auth-entry/AuthProvider.tsx` is not migrated for the same reason
  (lazy initializer, no persist effect, writes deliberately skipped for demo sessions); the
  duplicated `60vw` factor in `LeftRail.tsx:132` is not removed (ADR-260074 deliberately made that a
  zero-JS CSS `maxWidth`, so it cannot read the JS constant) — it gains a guard test only.
- Constraints (per EPIC-260082's adopted process change, **each of these gets a test named after it**
  at implementation time):
  - C1 — none of the seven `crystord-*` storage keys changes. Six e2e specs seed
    `crystord-home-emphasis` via `page.addInitScript`, and `e2e/left-rail-resize.spec.ts` depends on
    the width key surviving a reload, so a rename is invisible to Vitest alone.
  - C2 — `src/ui-shell/use-preferences.test.tsx` passes **byte-identical** through every migration
    task. Migration tasks may not edit it; that freeze is what makes the diff a proof.
  - C3 — every setter exposed on `WorkspacePreferences` keeps a stable identity across renders.
    `use-preferences.ts:184` memoizes on `setLeftRailWidth`, so an unstable setter produces a new
    context value every render for every `WorkspaceContext` consumer.
  - C4 — every value that reaches state has passed through `normalize`, on both the read and the
    write path (including the default fallback, which is clamped today at `use-preferences.ts:117`).
  - C5 — the first-render persist write is preserved for all six sites (the documented sticky-default
    semantics, `use-preferences.ts:19-22`). A natural-looking "skip the first write" guard would
    silently start delivering changed defaults to existing users.
  - C6 — `src/persistence` imports only `react`; `src/styles` does not import `src/ui-shell`.
  - C7 — `parse`, `serialize` and `normalize` are module-scope references at every call site.
- Dependencies: EPIC-260066 (`use-preferences.ts` origin, ADR-260061); EPIC-260077 / ADR-260073 /
  ADR-260074 (source of the `leftRailWidth` copy that prompted this); ADR-260047 (ThemeProvider and
  the token palette, migrated by T8); REQ-CR-260007 (frontend architecture boundary constraints —
  this epic adds a directory).
- Risks/assumptions: The assumption that one generic shape covers all six preferences was **tested,
  not assumed**, during ideation: a probe implementation was run against an unmodified copy of
  `use-preferences.test.tsx` (21/21 green). Two residual risks remain. (a) Setter referential
  stability (C3) is a call-site contract rather than a helper invariant, because the latest-ref
  pattern that would guarantee it is a hard ESLint error in this repo (`react-hooks/refs`, plugin
  v7 / React 19.2) — a future caller inlining `normalize: v => ...` gets a per-render re-render storm
  that no current lint or test would catch, which is why C7 exists. (b) `ThemeProvider` has **no unit
  test** (`src/styles/` contains only `label-colors.test.ts`), so T8 is the one migration with no
  behavioral safety net until T7 supplies one.
- Target window: TBD — not urgent; no open bug is currently caused by this, only closed ones and one
  latent one.
- Validation approach: the full existing `use-preferences.test.tsx` suite must pass with the file
  unmodified after every migration task; a characterization test for `ThemeProvider` written and seen
  green against the *unmigrated* file before T8; one named test per bug class written once against
  the shared helper so it covers every preference. Per EPIC-260082 findings 19/21, every guard test
  is verified to fail without its fix by reverting the source and re-running — a test that still
  passes with the fix reverted is labelled characterization and is not counted as a guard.

## Ideation Bullets — Resolved (2026-09-01, plan review; approved by the project owner this date)

- [x] **Helper shape: one generic hook plus pure parser factories, not a hook trio.** The final
  signature is `usePersistedState<T>(key, parse: (raw: string | null) => T, options?: { serialize?,
  normalize? }): [T, (value: T) => void]`, with three pure factories on top — `oneOf(allowed,
  fallback)`, `bool(fallback)`, `finiteNumber(fallback)`. The hook owns both try/catch blocks, the
  lazy `useState` initializer and the persist effect — the actual bug surface. A
  `usePersistedString`/`Boolean`/`Number` trio was rejected: `leftRailWidth` needs a
  `window.innerWidth` clamp, so the numeric variant would need a transform escape hatch anyway,
  giving three hooks *plus* the general case. Two corrections to the shape came out of ideation
  measurement. First, **`normalize` applies on init *and* on write**, not on write only: today's
  `readLeftRailWidth` clamps both the stored value (`:113`) and the default fallback (`:117`), and a
  write-only variant was built and measured to break `use-preferences.test.tsx:72-76` and `:92-102`,
  which C2 forbids editing. Second, **`parse`/`serialize`/`normalize` are documented as
  required-stable module-scope references** rather than laundered through a ref, because the ref
  version is a hard ESLint error here (see Risks). `serialize` defaults to `String`, which covers all
  six sites; the helper is documented as primitives-only, since `String({})` would silently yield
  `'[object Object]'` for a future object-valued preference. On a throwing `getItem` the hook calls
  `parse(null)` — one choice that reproduces today's behavior at all six sites *and* makes the
  missing-key and unavailable-storage paths agree by construction, which is precisely the invariant
  the two booleans violate today.
- [x] **Migration order: helper and coverage first, then three migration tasks — unions, booleans,
  `leftRailWidth`.** Three tasks rather than five: splitting the two booleans (or the two unions)
  apart produces a second diff that is the first with a different key constant — more review
  boundaries for no added information. Two departures from the order first proposed. The dedicated
  coverage task moves **before** the migrations (T2, not last): with coverage last, the epic spends
  its first review cycles on the migrations while the helper's own edge cases are unguarded, and
  three independent task drafts converged on this. And the **unions migrate before the booleans**:
  the union diff is provably behavior-identical (`oneOf` reproduces the existing validate-then-fall-
  through exactly), so it proves the helper against real call sites while carrying no semantic
  change, leaving the booleans' one deliberate semantic change (bullet 5) isolated in its own
  reviewable diff. `leftRailWidth` stays last — it is the only site with normalization on both paths
  and the one EPIC-260077 just hardened. Full suite green after each task.
- [x] **Where the helper lives: a new `src/persistence/` leaf module, not `src/ui-shell/`.** The
  bullet required checking rather than assuming, and the check found a genuine second consumer:
  `src/styles/ThemeProvider.tsx` is the same pattern (string-literal union, read-on-init,
  persist-in-effect, identical catch comments). That rules out `src/ui-shell/`: `ThemeProvider`
  importing from the shell would invert the established `ui-shell → styles` direction, and
  `src/ui-primitives/` is equally wrong because `architecture.test.ts:615-631` permits
  `ui-primitives → styles`, so `styles → ui-primitives` would close a directory-level cycle. The
  in-repo precedent for exactly this shape is `src/a11y/use-modal-focus.ts` (BI-260064) — a
  react-only leaf directory imported by both `ui-shell` and `features`. `ThemeProvider` is migrated
  by this epic (T8), keeping its `data-theme` DOM write as its own effect **declared before** the
  persist effect, preserving today's ordering and the property that a throwing `setItem` cannot
  prevent the DOM update. `api-contract/auth-token.ts` is explicitly excluded (see Non-goals).
- [x] **Coverage task: T2, before the migrations, one named test per bug class.** It targets the new
  helper and the three parsers directly — not "the same five preference tests happen to still pass".
  Named classes: unclamped fallback-to-default; empty/whitespace string parsing as a valid `0`;
  the boolean missing-key/`DEFAULT_*` mismatch; a formula duplicated across read and write. T2 also
  pins the two hazards those four classes do not cover — setter referential stability (C3) and
  first-render persist stickiness (C5) — because both regress silently and neither the frozen
  `use-preferences.test.tsx` nor a green suite would reveal them. Every guard is verified to fail
  without its fix.
- [x] **The boolean mismatch is fixed, not preserved — and that is this epic's one deliberate
  semantic change.** `bool(fallback)` returns the fallback for a missing or malformed value instead
  of collapsing everything non-`'true'` to `false`. It is observationally identical today (see the
  FINDING below), so it costs nothing and cannot be observed by any test — which is exactly why it
  must be stated here rather than discovered in a diff. Note for whoever later flips either default:
  the fix alone is insufficient, because the first-render persist effect has already cemented
  `'false'` in the storage of every user who has mounted the app even once; reaching them needs a
  migration, which is out of scope here.
- [x] **The two `architecture.test.ts` storage guards are retuned in T3, before any call site
  moves.** They fail in opposite ways and the quiet one is the dangerous one. `:2374` (ThemeProvider
  contains `'localStorage'`) hard-fails at T8 and cannot be missed. `:512-515` (use-preferences
  contains `'localStorage'`) **keeps passing after the migration on two doc-comment lines** — it goes
  silently vacuous, which a "full suite green after each task" gate cannot detect. Both are replaced
  by mechanism checks that prose cannot satisfy, the seven storage keys and all five `DEFAULT_*`
  constants are pinned by anchored regex (today only two are, and neither `DEFAULT_HOME_EMPHASIS` nor
  `DEFAULT_COMPUTE_BADGES` has any importer, so a fold-into-parser-call would drop them unnoticed),
  and a `src/persistence` boundary guard is added mirroring the `ui-primitives` one. Retuning an
  assertion must preserve its original intent — silently weakening one is a defect, not a fix.

**FINDING carried into this epic, reproduced not inferred (2026-09-01).** `readLeftRailCollapsed`
(`use-preferences.ts:91-98`) and `readRightRailCollapsed` (`:100-107`) place their
`return localStorage.getItem(K) === 'true'` *inside* the `try`, so that comparison is the function's
result on every non-throwing path and the trailing `return DEFAULT_*_COLLAPSED` is dead code —
reachable only when evaluating `localStorage` or calling `.getItem()` raises. The defect is properly
a **validation** defect, not a defaulting one: `=== 'true'` collapses `null`, `''`, `'TRUE'` and any
garbage to `false` with no validity check, whereas the file's other three readers and
`ThemeProvider.readStored` validate then fall through. It is **fully latent today, not merely rarely
hit** — because both defaults are `false`, exactly what `=== 'true'` returns for all those inputs,
the readers are observationally identical to a correct implementation for every possible storage
state. It becomes live the moment either constant is set to `true`. Verified by probe: with the
default flipped, a missing key yielded `false` and only the throwing path honoured the default.
Two things sharpen the risk. The existing suite does not protect this and actively misdirects —
`use-preferences.test.tsx:35-41` and `:43-49` assert the literal `false` rather than `DEFAULT_*`, so
with the defaults flipped they still **pass**, and the only failure is the throwing-storage test at
`:58`; the suite goes red where the code is correct and stays green where it is wrong. And no
consumer depends on the current behavior: `LeftRail.tsx:32` and `Inspector.tsx:28` only branch on the
boolean, nothing outside the hook writes those two keys, and both `DEFAULT_*_COLLAPSED` constants are
exported yet referenced nowhere but their own declaration and the dead trailing return.

**No ADR.** This is an internal-implementation refactor with no user-visible behavior, no public
interface, and no reversal of an Accepted decision — ADR-260061 records that preferences are
shell-owned and localStorage-backed, which this epic *implements* rather than changes. Precedent:
BI-260065 promoted duplicated auth UI into `ui-primitives` and BI-260064 created a new top-level
`src/a11y/` shared hook — both "no behavior change", both reusing existing ADRs, and `adr-index.md`
shows no ADR issued for either. The one arguably architectural element is the new dependency edge,
not the helper; this repo's instrument for that is an `architecture.test.ts` assertion (C6, T3),
which is exactly what BI-260064 did for `src/a11y/`. EPIC-260082's ICR process change
(diff `user-guide.md` alongside `schema.graphql`) is **not triggered** — this epic has no ICR and
touches no backend surface.
