# ADR-260061: Application Shell — Slot Registries, Workspace Context, and Node-Extension Seam

Status: Accepted
Date: 2026-06-30
Owners: Crystord App maintainers (info@aleutheris.com)

## Context

The deployed backend is pinned to schema 9.2.0 while the UI exposes roughly 30% of the product (atoms + labels + bonds). Closing that gap is organized as a 10-epic UI-exposure program (EPIC-260066–260075): one **Foundation** epic (EPIC-260066) plus nine mutually independent feature **leaves**. For the leaves to ship independently and not block each other, they must each plug a capability into a **stable shell** rather than restructure it.

The codebase already enforces the boundaries this requires:

- **Cross-feature import ban** and **`ui-shell` → feature-barrel-only** imports (`src/architecture.test.ts:35-82`).
- **`api-contract` is the only GraphQL boundary**; features map server types via adapters.
- **Dual-view shared selection** — a single `useGraphData` source and a `selectedAtomId` lifted to `WorkspaceShell`, fed to both canvases (ADR-260032 / REQ-FR-260034).
- **`ui-primitives/`** as a shared template library that features may import but which must not import feature modules (ADR-260051).

What is missing is the *structural spine*: today `WorkspaceShell` wires features ad hoc — a conditional `SearchResultPanel`, a single untabbed `DetailPanel`, two hardcoded canvas tabs in `GraphViewTabs`. Adding categories, compute, account, etc. on top of that would force each feature to restructure the shell and collide with others. We need extension points and shared-state contracts so a leaf adds a capability by *registration*, not surgery. **REQ-CR-260010 excludes a plugin-runtime system**, so the extension points must be compile-time, not a dynamic plugin host.

## Decision

Adopt a four-region application shell with three compile-time extension points, shell-owned shared state, and a node-extension seam.

1. **Four regions, each one job:** Top bar (context + query/facet chips · account menu), Left rail (navigate the *index*), Center view-host (represent the *working set*), Right inspector (inspect/edit the *selection*). Left and right rails are collapsible; collapsed state is persisted in preferences. The node-graph (Flow/Network) is home; the left rail is navigation only.

2. **Static typed slot registries in `ui-shell`** — one per slot: `navigators`, `views`, `inspectorTabs`. Each entry is a typed descriptor, refined per slot: `ViewDescriptor { id, label, enabled?, Component }`, `InspectorTabDescriptor { id, label, when?, Component }`, `NavigatorDescriptor { id, label, Component }`. Views carry an `enabled` availability gate — the `networkViewEnabled` flag lives in the view registry, so `enabled` is the **authoritative** gate and the shell derives the tab bar, the default view, and the active view from the enabled set; inspector tabs carry a per-atom `when?` relevance guard. The shell renders the active/eligible entries. **Navigators are scoping surfaces** — they browse the index and narrow the working set — so `NavigatorProps` is intentionally minimal (`{ atoms }`) for now and gains a scope/filter affordance once the shared filter builder defines the filter shape (T8 / EPIC-260068); it is **not** an atom-picker contract. A leaf registers by exporting its component from its feature barrel and adding one descriptor entry. This is **compile-time composition, not a runtime plugin registry** (which would invert the enforced `ui-shell → feature` dependency direction and is the "plugin runtime system" REQ-CR-260010 forbids). It generalizes the existing dual-view pattern: `GraphViewTabs` is driven by the views registry (its view list is no longer hardcoded), and the same descriptor model extends to the navigator and inspector slots.

3. **Shell-owned `WorkspaceContext`** exposing `{ workingSet, selection, preferences }`, consumed by slot components:
   - **workingSet** — filters → atoms in scope, backed by the existing `useSearch` / `useGraphData`.
   - **selection** — `selectedAtomId` is owned by `WorkspaceContext` and provided by the shell. `ui-shell` host components (the inspector, and later the rails) consume it via `useWorkspace()`; feature view components still receive it via `ViewProps`, since features must not import `ui-shell`. This **updates**, not violates, the ADR-260032 shared-selection model — the same single source, now delivered via context to shell hosts as the consumer set grows.
   - **preferences** — a new **localStorage-backed store modeled on `ThemeProvider`** (it is *not* an extension of the single-line `feature-flags.ts`). Keys `homeEmphasis` (default `compute`) and `computeBadges` (default `always`), per the Q3 compute-as-differentiator lean. EPIC-260066 ships the contract + defaults; EPIC-260070 adds the toggle UI; EPIC-260069 reads the default.

4. **`AtomNodeData` node-extension seam** — `AtomNode` is restructured into three named regions — `handles` · `badges` · `body` (the title is the body's header line) — over a stable, **open** `AtomNodeData` contract (`[key: string]: unknown`) whose named extension points are `computeStatus` (→ badges) and `lod` (→ body), their shapes defined by the consuming epics. EPIC-260069 (Compute) writes the `badges` region; EPIC-260072 (LOD/Blender blocks) owns the `body`. Because they fill different regions, the two leaves extend the node without colliding. Implemented on the Flow node (`AtomNode`). The Network node (`CircleAtomNode`) gains the same seam when compute/LOD reach the Network view — deferred, since compute is primarily a Flow concern (Q3) and `CircleAtomNode` carries complex interaction logic best left untouched until there is a consumer.

5. **Shared widgets live in `ui-primitives/`** (consistent with ADR-260051's no-feature-import rule), built **presentational** — data and callbacks injected, data hooks stay in `api-contract`/feature wiring. The kit: the filter builder, the permission-aware category tree, and the label chip editor, reused across search, the category navigator, and COLLECT. Shipped as **style-neutral** shells (structure + a11y + `classNames`, matching `LabeledField`), with the shared contracts defined: `WorkspaceFilter` (labels + category facets, mapping `retrieve(categories:)`), `CategoryTreeNode` (mapping `retrieveCategoryBrowse`), and a `canEditNode?` permission seam (Q2). Leaves wire data + styling; EPIC-260068 fills the filter builder's category-facet slot and adds the navigator scope affordance against `WorkspaceFilter`.

6. **Demote `SearchResultPanel`** out of the left rail; the working set is represented by the active center view (the graph re-scopes on search today; the flat list returns as the Table view, EPIC-260071).

This ADR **extends** ADR-260032 and **reconciles/cites** ADR-260051; it supersedes neither.

## Alternatives Considered

- **Runtime plugin registry** (features push into a shared mutable registry): rejected — inverts the enforced `ui-shell → feature-barrel` direction, isn't statically analyzable, and is the "plugin runtime system" excluded by REQ-CR-260010.
- **Keep ad-hoc per-feature shell wiring**: rejected — every new feature restructures `WorkspaceShell`, causing collisions and defeating independent, non-blocking leaf delivery.
- **Prop-drill shared state to every view/tab**: rejected — unmanageable as slots multiply (N views × M tabs); context keeps the shell the single composition owner.
- **Put shared widgets in a feature module**: rejected — violates the cross-feature import ban; `ui-primitives` is the sanctioned shared home (ADR-260051).

## Consequences

- Positive: leaves ship independently as registrations; the enforced architecture boundaries continue to hold; minimal new concepts (the registries generalize an existing pattern; preferences mirror `ThemeProvider`); the node seam lets two leaves extend `AtomNode` without coupling.
- Negative: a one-time `WorkspaceShell` refactor; the ADR-260032 architecture assertion that checks `selectedAtomId` is passed *as props* must be rewritten to assert the context provider (done in EPIC-260066 T3).
- Risks: the `AtomNodeData` seam must be right because two later epics depend on it; the selection→context migration must keep all existing E2E green. Both are mitigated by staging the work across tasks T2–T9 with the E2E suite as the regression gate on each.
- Invariant (view-host): the shell derives the default and active view from the enabled set, and relies on `enabledViews` (`slots/view-registry.ts`) being non-empty — Flow is unconditionally enabled there. `WorkspaceShell`'s `enabledViews[0]!` / `?? 'flow'` fallbacks are defensive no-ops resting on that guarantee (documented at the assertion site; two provably-unreachable branches carry a coverage exemption in EPIC-260066/T9). **If a later epic ever gates Flow, the latent empty-`enabledViews` crash and that exemption must both be revisited.**

## Verification

- All existing E2E specs (sign-in, graph-workspace, search, create-atom) stay green throughout the shell refactor.
- New architecture tests assert the three registries exist and that feature leaves register through them with no cross-feature imports.
- A selection-via-context parity test replaces the ADR-260032 props assertion (both canvases + all views/tabs read the same `selectedAtomId` from `WorkspaceContext`).

## Rollback

The registries wrap existing components rather than replacing them, so reverting is restoring direct wiring in `WorkspaceShell`. Work is staged as small, reversible per-task PRs; if outcomes are poor the epic can return to Ideation (status in `epic-index.md`) and individual task commits reverted without touching feature modules.
