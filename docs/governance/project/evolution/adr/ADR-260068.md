# ADR-260068: Per-Atom Change History Surface

Status: Accepted
Date: 2026-07-18
Owners: Crystord App maintainers (info@aleutheris.com)

> Approval note: accepted under the project owner's batch delegation of 2026-07-17 covering
> the UI-exposure program's plan/decision approvals (recorded in `epic-index.md`).

## Context

The backend records field-level change history — a branding pillar ("Transparency") — that
is completely invisible in the UI. Schema facts: `ShelliesOutput.changes(limit: Int = 5,
offset: Int = 0): [ChangeEvent!]` with `timestamp`, `eventType`, `userId`, `remark`,
`propertyChanges { field, oldValue, newValue, metrics { removedCount, addedCount,
totalMembersAfter } }`; events return **newest-first**; there is **no total count** for
pagination and **no user-lookup query** to resolve `userId` to a display name. The `change`
mutation's optional `remark` feeds `ChangeEvent.remark`.

## Decision

1. **A read-only History inspector tab** (feature `workspace-history`, registered `history`
   after Compute) lists the selected atom's change events newest-first (server order
   rendered as-is): localized timestamp · eventType chip · remark (when present, italic) ·
   per-property rows `field: old → new` (JSON stringified, truncated, full value in the
   tooltip) · a compact metrics line for list-type fields.
2. **Dedicated lean query.** New api-contract `history-operations.ts` with an
   `ATOM_CHANGES_QUERY` — `retrieve(uuid)` selecting **only** `properties { shellies { uuid
   changes(limit, offset) { … } } }` — fetched network-only on tab mount per atom. The
   working-set `RETRIEVE_QUERY` stays lean (history is on-demand, per-atom).
3. **Page-size-probe pagination.** Page size 10; "Show more" appends the next offset;
   end-of-history is inferred when a page returns fewer than `limit` — the only option
   without a total count (documented limitation). A refresh affordance re-fetches from
   offset 0.
4. **Honest identity display.** `userId` renders shortened (monospace, full id in the
   tooltip). Resolving display names has no schema support — recorded as a backend
   follow-up, not faked client-side.

## Alternatives Considered

- **Selecting `changes` on the working-set query:** rejected — pays the history cost on
  every search for every atom; history is a per-atom, on-demand read.
- **Client-side userId→username guessing** (e.g. matching `ownerUuid`): rejected — partial
  and misleading; the honest shortened id keeps the audit trail truthful until the backend
  exposes a lookup.
- **Infinite scroll:** rejected — "Show more" is deterministic and testable given blind
  (no-total) pagination.

## Consequences

- Positive: the transparency pillar becomes visible; remarks entered via `change` finally
  surface; the lean dedicated query keeps the working set unaffected.
- Negative: blind pagination shows a "Show more" that may fetch an empty page at the exact
  boundary (accepted; the button hides once a short page arrives).
- Risks: `changes` list is nullable in the schema — treated as empty.

## Verification

- Unit: event rendering (timestamp/eventType/remark/property rows/metrics), newest-first
  order preserved, pagination append + end detection (short page, exact-boundary empty
  page), refresh reset, nullable-changes tolerance, error surfacing.
- E2E: edit an atom, open History, see the event (mocked changes echo); Show more flow.
- Architecture: `workspace-history` module/barrel/registry; ATOM_CHANGES_QUERY selects
  changes but not nuclearies; read-only (no mutations in the feature).

## Rollback

The tab registers additively; removing the descriptor + feature dir + api-contract module
reverts the surface completely.
