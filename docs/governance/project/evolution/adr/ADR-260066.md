# ADR-260066: Account Menu Consolidation and Modal Settings Surfaces

Status: Accepted
Date: 2026-07-18
Owners: Crystord App maintainers (info@aleutheris.com)

> Approval note: accepted under the project owner's batch delegation of 2026-07-17 covering
> the UI-exposure program's plan/decision approvals (recorded in `epic-index.md`).

## Context

The top-right header is three loose controls (`ThemeToggle`, an Account button opening
`AccountSettingsPanel`, Sign Out) with no room to grow; the backend's workspace layer
(`listMyWorkspaces`, members/roles CRUD) has no UI; and the Q3 emphasis switches
(`homeEmphasis`, `computeBadges` — consumed by EPIC-260069) have no toggle surface.
**Schema fact:** there is no current-workspace/session-context concept — workspaces exist
only as sharing principals plus membership, and `retrieve` takes no workspace argument, so
"switching workspaces" has nothing to bind to. EPIC-260066 deliberately shipped no top-bar
slot; the header is shell chrome.

## Decision

1. **One avatar menu** (`AccountMenu`, new in `ui-shell` — it composes feature barrels and
   shell preferences, i.e. shell chrome like the header it replaces). Trigger: an avatar
   button (username via `useAccountInfo` once loaded; generic glyph before). Menu
   (`role="menu"`, ArrowUp/Down + Home/End + Escape + click-outside): identity header
   (username · email, non-interactive) → Theme (cycling item showing the current mode,
   replacing the standalone `ThemeToggle` in the header) → Account settings → Workspaces →
   Preferences → separator → **Sign Out pinned last**.
2. **Reshape the header directly** — no top-bar slot. A registry with one consumer would be
   speculative structure (REQ-CR-260010 lean); ADR-260061's slots stay left/center/right.
3. **Preferences = a shell-owned modal** (`PreferencesPanel` in `ui-shell`): theme mode plus
   the `homeEmphasis` and `computeBadges` switches writing the EPIC-260066 preferences
   contract (features must not import ui-shell, so this surface cannot live in a feature).
   **No display-density setting** — not in the shipped contract; adding a key now would be
   speculative.
4. **Workspaces = management, not switching.** New feature `workspace-admin` (modal): list
   my workspaces + create; per-workspace rename/description, member list, add member by
   username + role, change role, remove member, dissolve (two-step confirm). The caller's
   role derives from matching `me.username` in the member list (the schema exposes no
   caller-role field); backend errors surface via the central mapper (raw message for
   unrecognized codes). New api-contract module `workspace-operations.ts` holds the
   documents + types. Workspace *switching* is recorded as a backend-dependent future
   (would need a schema ICR).
5. **Account settings unchanged** — the existing `AccountSettingsPanel` (ADR-260058) opens
   from the menu instead of a bare header button.

## Alternatives Considered

- **A top-bar slot registry:** rejected — single consumer today; speculative structure.
- **Workspace switching UI:** rejected — no backend current-workspace concept; building a
  client-side illusion (compose `listAtomsSharedToWorkspace` + per-uuid retrieve) would
  misrepresent the data model. Future schema ICR if the concept lands.
- **Routing settings pages instead of modals:** rejected — the app is a single workspace
  surface (ADR-260017 lineage); `AccountSettingsPanel` set the modal precedent.
- **A display-density preference:** rejected — not in the preferences contract; no consumer.

## Consequences

- Positive: one coherent account surface; the Q3 switches become user-visible; the
  workspace layer gets its first UI; the header stops accumulating loose buttons.
- Negative: Sign Out moves behind one click (mitigated: pinned, separated, bottom — a
  stable muscle-memory position); every E2E that used the visible Sign Out button as the
  authenticated sentinel must go through the menu.
- Risks: menus are an a11y hot spot — the roving-focus/Escape pattern follows the existing
  tablist/modal precedents (`useModalFocus` for the modals, arrow-key roving for the menu).

## Verification

- Unit: menu open/close/keyboard/roving focus; Sign Out pinned last; theme cycle item;
  PreferencesPanel writes all three preferences; workspace-admin flows (list/create/members
  add-remove-role/dissolve confirm) incl. error surfacing and self-role derivation.
- E2E: menu-driven account-settings open; toggling emphasis in Preferences flips the
  landing view on next load; workspace create + member add against mocks; sign-out via menu.
- Architecture: `workspace-admin` module/barrel; shell renders `AccountMenu` and no longer
  the three loose controls; menu keyboard pattern present.

## Rollback

The menu is a header-local composition: restoring the three buttons and removing
`AccountMenu`/`PreferencesPanel`/`workspace-admin` reverts the surface; `workspace-operations.ts`
is additive api-contract.
