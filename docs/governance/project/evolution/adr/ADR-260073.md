# ADR-260073: Resizable Left Rail — Bounds, Persistence, and Keyboard Grammar

Status: Accepted
Date: 2026-08-27
Owners: Crystord App maintainers (info@aleutheris.com)

> Approval note: accepted 2026-08-27 on the project owner's explicit delegation, after the owner
> reviewed and confirmed all seven ideation bullets this ADR encodes.

## Context

The left rail (`LeftRail.tsx`) hosts the Labels/Categories navigator lenses at a fixed `240px`
width, with no user control over it. EPIC-260076 added dimension nesting on top of value nesting
in the Categories tree (`CategoryTree`'s `indentOption`, 4 non-breaking spaces per depth level),
so two compounding levels of hierarchy now render inside the same fixed-width column — display
names truncate or wrap sooner than they did with a flat taxonomy.

The right rail (`Inspector.tsx`) has the identical fixed-width pattern (`width: 320`) but was not
part of the reported problem and is explicitly out of scope here (EPIC-260077's first ideation
bullet).

## Decision

### D1: Scope — left rail only
This ADR and its epic (EPIC-260077) cover `LeftRail.tsx` exclusively. The right rail is not
touched. The mechanism (clamp function, preference shape, handle component) is expected to be
reusable if the right rail needs the same treatment later, but that is a distinct future epic, not
assumed scope here.

### D2: Width bounds
- Default remains `240px`, unchanged for any user who never touches the handle — consistent with
  every other preference in `use-preferences.ts` being a sticky default written on first render.
- Minimum `200px`: below this the lens switcher tabs and `CategoryNodeEditor`'s
  `width: '100%'` inline inputs become uncomfortably cramped.
- Maximum `480px`, further capped at 60% of the current viewport width
  (`clampLeftRailWidth(width, viewportWidth) = clamp(width, 200, max(200, min(480, 0.6 * viewportWidth)))`).
  The viewport-relative cap prevents the rail from crushing the center canvas on a narrow browser
  window without building a dedicated narrow-viewport/responsive feature.
- The clamp is applied consistently: reading a persisted value, dragging, keyboard stepping, and
  reset all funnel through the same `clampLeftRailWidth` function — there is exactly one source of
  truth for "what width is valid," not separate validation at each call site.

### D3: Persistence
`use-preferences.ts` gains `leftRailWidth: number` and `setLeftRailWidth(value: number): void`,
stored under a new `crystord-left-rail-width` localStorage key, following the exact
read/write/try-catch shape and sticky-default caveat already established for
`leftRailCollapsed`/`rightRailCollapsed`/`homeEmphasis`/`computeBadges` in the same file. No
server-side or per-workspace persistence — this is a cosmetic, client-local layout preference, not
a contract the backend needs to know about.

### D4: Keyboard grammar
The resize handle is a WAI-ARIA `separator`: `role="separator"`, `aria-orientation="vertical"`,
`aria-valuenow`/`aria-valuemin`/`aria-valuemax` reflecting the live/clamped width, focusable
(`tabIndex={0}`), with a visible focus indicator matching the pattern already used by
`GraphViewTabs`'/`LeftRail`'s own lens-switcher tabs. Keyboard grammar:
- `ArrowLeft` / `ArrowRight` — nudge width by a fixed step (`16px`).
- `Home` / `End` — jump to the effective min/max.

This is a deliberate consistency call: every other interactive control in this shell
(`GraphViewTabs`, `LeftRail`'s own lens tablist, `CategoryTree`'s tree role) is keyboard-operable,
and a mouse/pointer-only resize handle would be the first exception. The keyboard path reuses
`clampLeftRailWidth` (D2), so it cannot diverge from the pointer-drag path's bounds.

### D5: Reset affordance
Double-clicking the handle resets width to the `240px` default. Matches the conventional pattern
for this kind of control (VS Code, browser devtools split panes).

### D6: Granularity — single shared width
The rail is one `<aside>` shared by both the Labels and Categories lenses (`LeftRail`'s lens
switcher). Width is a single shared preference, not per-lens. A per-lens width would make the rail
visibly jump on every lens switch, and nothing in the reported problem calls for lens-specific
widths — the same "don't build unrequested orientation/mode toggles" restraint ADR-260039 applied
to Flow view's LR/TB decision.

### D7: Collapse/width independence
`leftRailCollapsed` and `leftRailWidth` are independent preferences with no cross-dependency:
collapsing hides the rail entirely (unchanged existing behavior); expanding restores it at
whatever width was last set, never resetting to default. No special-casing required — this falls
out naturally from treating them as two separate `useState`s in the same hook, exactly like every
other pair of preferences in that file already behaves.

## Alternatives Considered

- **Resize both rails in this epic:** rejected (D1) — no validated need for the right rail, and it
  would double the surface area (tests, a11y grammar, bounds decisions) for an unreported problem.
- **Fixed max width with no viewport-relative cap:** rejected — a flat `480px` (or `560px`) max is
  simpler but doesn't scale down on a narrow window; would need a separate narrow-viewport
  carve-out later to fix what the 60vw cap prevents from being a problem in the first place.
- **Server-side/per-workspace width persistence:** rejected (D3) — disproportionate for a cosmetic
  layout preference; would require an ICR for no behavioral benefit over localStorage.
- **Defer keyboard accessibility to a later pass:** rejected (D4) — would be the first
  mouse-only interactive control in a shell that has been keyboard-operable throughout; the
  marginal cost is low since it reuses the pointer path's clamp function.
- **Per-lens width:** rejected (D6) — see above; adds complexity and a jarring lens-switch
  side-effect for a capability nobody asked for.

## Consequences

- Positive: deep/wide category trees become readable at a user-chosen width; the resize mechanism
  and clamp function are reusable if the right rail needs the same treatment later; keyboard users
  are not second-class citizens for this control.
- Negative: one more piece of persisted client state to reason about (`leftRailWidth`); the rail's
  layout math (handle position, aside width) adds a small amount of complexity to `LeftRail.tsx`.
- Risks: a viewport resize *after* a width was persisted is not reactively re-clamped (the cap is
  applied at the moment width changes — drag, keyboard step, reset, or read-on-mount — not on a
  live `window.resize` listener). This is a deliberate scope boundary, not an oversight: the
  center canvas uses `flex: 1` and simply shrinks to accommodate, so an unclamped-until-next-change
  width is a minor cosmetic edge case, not a broken layout.

## Verification

- Unit: `clampLeftRailWidth` bounds behavior (below min, above max, above viewport cap, valid
  passthrough); `use-preferences.ts` persistence (default, round-trip, invalid-stored-value
  fallback, localStorage-unavailable fallback) mirroring the existing preference tests' shape.
- Unit: keyboard grammar (arrow-key step, Home/End, double-click reset) via the shared clamp path.
- E2E: pointer drag-resize changes rendered width; width survives a reload (persistence).
- Regression: existing `LeftRail` collapse/lens-switcher tests remain green; Inspector (right
  rail) untouched.

## Rollback

Remove the handle from `LeftRail.tsx` and the `leftRailWidth`/`setLeftRailWidth`/
`clampLeftRailWidth` additions from `use-preferences.ts`; the rail reverts to a fixed `240px`.
Any already-persisted `crystord-left-rail-width` localStorage value becomes inert (harmless to
leave behind — same pattern as every other preference key in this file).
