# ADR-260071: Categories Navigator — Hierarchical Dimensions, Lazy Browse Tree, Facet Scoping, and Inline Taxonomy Authoring

Status: Accepted
Date: 2026-07-21
Owners: Crystord App maintainers (info@aleutheris.com)

> Approval note: accepted 2026-07-21 on the project owner's explicit delegation, after the owner
> resolved every ideation bullet this ADR encodes and reviewed the implementation across three
> rounds. The permission decision in §6 came from the backend team, not from inference.

> Supersedes ADR-260064. That record decided a **flat** dimension top level; this one replaces it
> with a dimension hierarchy. ADR-260064's other decisions (facet scoping contract, chips and
> re-fetch, inline authoring, real permission gating, lens switcher) are carried forward here
> unchanged so this ADR is the single source of truth for the navigator — per the artifact model's
> whole-record supersede rule, which has no "partially revised" state.

## Context

ADR-260064 shipped the Categories navigator with dimensions as a flat top level. That was a
frontend scope choice for EPIC-260068, not a limit of the data model — and it does not survive
contact with real taxonomies. A user modelling `Region ▸ Country` finds no way to express it,
and misreads the per-node editor's "add value" form as dimension creation.

The backend has supported the hierarchy since schema 9.2.0 and requires **no change**:

- `createCategoryDimension(key, displayName, description, parentDimensionKeys, childDimensionKeys)`
  wires a new dimension into the schema atomically.
- `connectCategoryDimensions` / `disconnectCategoryDimensions` add and remove `UNDER_CATDIM`
  edges; disconnecting to no parent makes a dimension a root.
- `CategoryDimensionOutput.parentDimensionKeys` is already selected by the frontend — **and
  discarded**.

Dimension nesting and value containment are validated independently. Dimension operations check
only existence, single-parent (`CAT-MULTIPLE-PARENTS-UNSUPPORTED`), and acyclicity
(`CAT-DIMENSION-CYCLE`); they never inspect values. `CAT-VALUE-PARENT-DIMENSION-MISMATCH` is
reachable only from value operations. A value with no parent value is the normal root case and is
exactly what `retrieveCategoryBrowse(dimensionKey)` returns as its top-level entry points.

## Decision

1. **Dimensions form a single-parent tree.** The navigator's top level is *root* dimensions;
   a dimension may nest under one parent. The tree is assembled **client-side** from
   `retrieveCategoryDimensions` + `parentDimensionKeys` — `retrieveCategoryBrowse(dimensionKey)`
   returns a dimension's root *values*, never its child dimensions. Per-node lazy value loading is
   unchanged: a nested dimension loads its values on expand exactly as a root one does.
   *(Replaces ADR-260064 §1's flat top level; the lazy value-browse mechanics are retained.)*
2. **Create-with-parent is atomic.** `AddDimensionForm` gains an optional parent selector passed
   as `parentDimensionKeys` on `createCategoryDimension`, so building a tree top-down is one step
   and never leaves a transient orphan.
3. **Re-parenting is form-based, and a move is two calls.** `CategoryNodeEditor` gains a parent
   selector plus "detach to root". Re-parenting is done **from the child**: to nest B under A you
   edit B. The schema's `childDimensionKeys` (wiring from the parent's side) is not exposed and not
   declared in the documents — it would be a second control for a capability already reachable.
   Attaching a *root* dimension is one `connectCategoryDimensions` call; **moving an
   already-parented dimension is `disconnect` then `connect`**, because connecting over an existing parent returns
   `CAT-MULTIPLE-PARENTS-UNSUPPORTED`. The UI presents this as one action and reports the
   partial-failure state honestly (the dimension is left a root). Drag-and-drop remains out of
   scope — ADR-260064 judged it disproportionate for this rail and nothing has changed.
4. **Dimension error codes are mapped, as defense in depth.** `CAT-MULTIPLE-PARENTS-UNSUPPORTED`
   and `CAT-DIMENSION-CYCLE` get readable, user-facing messages. The UI is built so neither is
   reachable in a single session — cycle targets are filtered out of the selector, and a move
   always disconnects first — so these are the safety net for races (a concurrent edit from another
   client) and stale data, not the primary path. `CAT-VALUE-PARENT-DIMENSION-MISMATCH` stays on
   the generic path — it cannot be produced by a dimension operation.
5. **Facet semantics are unchanged.** OR within a dimension, AND across dimensions,
   `includeDescendants` on the **value** axis only. A nested dimension is filtered independently;
   selecting a parent dimension does *not* implicitly pull in child dimensions' values. Extending
   `includeDescendants` to the dimension axis is a distinct feature that would change behavior
   users already rely on. *(Carried forward from ADR-260064 §2–§3, explicitly scoped.)*
6. **Real permission gating.** `canEditNode` = the node's real `accessLevel` ∈ {OWNER, EDITOR}
   from `Category*Output.accessLevel`. Taxonomy share/transfer UI stays out of scope.
   *(Carried forward from ADR-260064 §5.)*

   Re-parenting carries a **stricter gate than editing** (confirmed with the backend team,
   2026-07-21). `connectCategoryDimensions` requires **OWNER** on the dimension being moved — a
   bare `OWNS` edge, so an EDITOR grant is *not* sufficient — and only **read** access on the
   target parent. Therefore:

   - The move form is gated on `accessLevel === 'OWNER'`, independently of `canEditNode`, which
     admits EDITOR and remains correct for rename and add-value.
   - Parent candidates are **not** filtered by access level: read is enough for a parent, and the
     server only returns dimensions the caller can read, so every listed option is already valid.
   - The gate must come from `CategoryDimensionOutput.accessLevel`, never from the error response.
     A non-owned child and an unreadable parent both return the same not-found error as a genuinely
     missing dimension — deliberately, so the response cannot disclose which — making it useless
     for driving affordances and impossible to turn into an honest message after the fact.

   This is live, not theoretical: `shareCategoryDimension` already grants EDITOR, so any EDITOR
   grant would make an "edit rights" heuristic offer moves that always fail.

   The same asymmetry is why `childDimensionKeys` stays unexposed (§3). The check follows the
   *child* of each pair, so "attach children under this dimension" needs OWNER on **each child**
   and only read on the dimension being edited — you can hang dimensions you own beneath one you
   merely read. An affordance gated on the edited node would be wrong in both directions.

7. **Lens switcher and rail scope.** The registry-driven Labels | Categories lens switcher stands;
   atoms under a node are still not listed in the rail — navigators scope, views represent.
   *(Carried forward from ADR-260064 §1 and §6.)*

## Alternatives Considered

- **Multi-parent dimensions (DAG):** rejected for v1 — the backend is single-parent
  (`CAT-MULTIPLE-PARENTS-UNSUPPORTED`); the list-shaped arguments are DAG-ready but the tree is not.
- **Server-side dimension tree:** not available — browse returns a dimension's values, not its
  child dimensions, so assembly is necessarily client-side.
- **Two explicit steps for a move (detach, then attach):** rejected — simpler to build, but it
  surfaces an API constraint as user work and produces the dead-end interactions this navigator has
  already suffered from.
- **Detecting stale `UNDER_CATVAL` edges after a re-parent:** deferred — re-parenting does not
  revalidate value edges, so a value can retain a parent outside the immediate parent dimension.
  It affects only already-populated dimensions, is recoverable through the value editor, and no
  detection or cleanup ships in v1.
- **Extending `includeDescendants` to the dimension axis:** deferred — see §5.

## Consequences

- Positive: taxonomies can express real structure; the capability needs no backend work and no
  ICR; `parentDimensionKeys` stops being fetched-and-discarded; the editor's ambiguous stacked
  forms get disambiguated in the same pass.
- Negative: the client owns tree assembly (and its cycle-safety); a move is non-atomic and the UI
  must carry a partial-failure state that has no server-side equivalent.
- Risks: client-side tree building must be cycle-safe even though the server rejects cycles —
  stale or concurrent data could still present one. Covered by dedicated unit tests.

## Verification

- Unit: tree builder (roots, nesting, cycle-safe traversal); mapping of the two dimension error
  codes; unchanged facet-selection semantics.
- E2E: create under a parent; attach a root to a parent; detach to root; move an already-parented
  dimension (two-call path); and a refused attach mid-move, asserting the partial-failure wording.
  The two `CAT-*` mappings are covered at the unit level: neither is reachable through the UI (§4),
  so an end-to-end path for them would have to mock a server the UI prevents you from provoking.

## Rollback

The parent selector and re-parenting controls are additive UI over existing operations; removing
them restores the flat rail. `parentDimensionKeys` on create is optional and harmless to keep.
Nothing in the data model is written that the previous flat UI cannot tolerate — a nested
dimension simply renders as another root once the tree builder is removed.
