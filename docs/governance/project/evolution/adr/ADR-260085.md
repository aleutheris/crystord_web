# ADR-260085: In-App Help — Standalone Entry Point, Centered Modal, Registry-Keyed Typed Content

Status: Accepted
Date: 2026-09-01
Owners: Crystord App maintainers (info@aleutheris.com)

> Approval note: accepted 2026-09-01 with the project owner's approval of EPIC-260080 into
> `Ready`; D4 is the one decision the approved bullets did not name, and was approved separately
> at the implementation-review gate on 2026-09-02.

## Context

The workspace shell shipped eleven feature epics with no in-product explanation of what anything
means. A user who opens the app cannot learn from inside it what an Atom, a Bond or a Dimension
is. Documentation for this reader has never existed.

`docs/user-guide.md` is not a stale version of it — it is the backend behavior contract, written
for developers building against the GraphQL API, in vocabulary (`properties.shellies`,
`operation`) that reaches no user-visible label in `src/`. The two documents serve different
readers and are both correct.

Shipped surfaces, read from the registries: four center views (Network, Flow, Table, Board), five
inspector tabs (Details, Classify, Compute, History, Share), two navigator lenses (Labels,
Categories).

## Decision

**D1 — One standalone `?` button in the header, before `AccountMenu`.** Rejected: an item inside
`AccountMenu`. The epic's success metric is help reachable in one click, which a menu item fails
at two. The button carries an explicit accessible name, like every other icon-only control in
this header (ADR-260031's a11y floor). Placing it before `AccountMenu` keeps `Account menu` the
rightmost control, which five e2e specs use as their authenticated sentinel. This does not reopen
ADR-260066, whose binding scope is the top-right account cluster, not the header.

**D2 — The existing centered-modal panel, not a route.** ADR-260066 already rejected routing this
class of surface; the router was removed in `7443cb2`; and a panel preserves workspace state by
construction, since it mounts as a sibling of the workspace tree. Focus, the Tab trap, Escape and
focus-restore come from `a11y/use-modal-focus.ts`, as they do for `PreferencesPanel`.

**D3 — Typed TypeScript content, keyed to registry ids, co-located with the surface's owner.**
Concepts first, then one section per surface. The heading is the descriptor's own `label` and
`HelpSection` has no `title` field, so renaming a surface renames its heading. Content is `.ts`
not `.md`: no markdown renderer is a dependency, and `.md` would make D5's compile-time gate
impossible.

**D4 — `src/help/` is a new leaf module holding the content types and concepts copy.** The shared
`HelpSection` type cannot live in `slot-types.ts`, because a feature module must not import
`ui-shell` and D3 requires features to author their own copy. A leaf that imports nothing and is
imported by both sides is the only shape that keeps the direction intact. Precedent: `src/a11y/`.

**D5 — `help` is a required field on all three slot descriptors.** Registering a surface without
it is `TS2741`. One runtime test asserts each `help.body` is non-empty over the **imported**
registries — never over file text, which is the shape EPIC-260078 documented going vacuous.

**D6 — A table of contents with anchors, no search, opening on the active view's section.** At
~4,700 words across seventeen sections, search solves a problem that does not exist. Contextual
open stops at the center view because `activeView` is already shell state; `activeTabId` and
`activeLensId` are component-local, and reaching them means changing a shell contract with three
consumers — the epic's recorded open question.

## Alternatives Considered

- **A help item inside `AccountMenu`:** rejected — two clicks fails the metric, and it churns the
  exact label and roving-tabindex arrays `AccountMenu.test.tsx` pins.
- **A `/help` route:** rejected — reopens an Accepted decision, has no router to run on, and
  empties a working set that only repopulates on an explicit search.
- **Markdown content with a runtime renderer:** rejected — a new dependency for static prose, and
  it forfeits the compile-time gate.
- **A central content directory:** rejected — moves the help diff out of the line of sight of the
  reviewer already reading that feature's changes.
- **For D4 — the type in `slot-types.ts`** (inverts the dependency direction), **in
  `ui-primitives`** (a content type is not a UI primitive), or **declared per feature**
  (structural typing then permits three drifting shapes).

## Consequences

- Positive: help is one click away and never costs the user their place. Adding a surface without
  help is a compile error rather than a review oversight, and renaming one renames its heading.
- Negative: every future view/tab/lens must author copy before it compiles. Five test fixtures
  gained a `help` field.
- **The gate proves presence, not truth.** Nothing catches a section that has quietly become
  untrue — `1d08b63` inverted what a Flow arrow means in 21 lines with the registry byte-identical.
  The only instrument is the process obligation in `project-instructions.md` §6, which is a human
  check. There is no compiler for "this sentence is still accurate", and this record does not
  claim one. The app is in beta and the copy is expected to lag the code a little.
- **D3's rename guarantee reaches headings only.** Prose that names another surface or control is
  an ordinary string literal that nothing updates. Interpolating labels into prose was rejected as
  worse than the problem; §6 names renames explicitly instead.
- **"One click from anywhere in the shell" means the shell, not every app state.** Behind an open
  modal, help is two interactions away — as is every header control, `AccountMenu` included.
- Help documents the views a user can actually reach (`enabledViews`), while the presence gate
  runs over the full `views` registry.

## Verification

Unit: dialog role, `aria-modal`, accessible name, the three close paths, focus in and restore,
the scrolling body as a keyboard-reachable region, headings driven by descriptor `label`
(asserted against a renamed fake registry), and contextual open as a pure function. Registry: a
non-empty `help.body` on every registered surface and concept, over imported data. Shell: the
entry point's presence and DOM position, and help rendering outside the workspace subtree. E2E:
one-click open, and the workspace surviving open-and-close.

**Not** a coverage claim: whether the prose is true.

## Rollback

Remove the `?` button, the `{isHelpOpen && <HelpPanel …>}` sibling, the `isHelpOpen` state and the
`HelpPanel` import from `WorkspaceShell.tsx` — all four together, or the build goes red on unused
symbols — plus the help tests in `WorkspaceShell.test.tsx` and `e2e/help.spec.ts`. Removing the
content itself is a second step: make `help` optional, drop it from the registries, and delete
`src/help/`, `src/ui-shell/help/`, `labels-navigator-help.ts` and the nine feature `help.ts`
modules.
