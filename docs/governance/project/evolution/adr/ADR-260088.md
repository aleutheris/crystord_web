# ADR-260088: Relationship Emphasis (Network) as the Default Landing View

Status: Accepted
Date: 2026-09-08
Owners: Crystord App maintainers (info@aleutheris.com)

## Context

ADR-260065 §7 wired `homeEmphasis` to the initial active view and set the shipped default to
`compute` (Flow), per the Q3 "compute-as-differentiator" lean recorded in that ADR's context.
The product direction has since changed: relationships (Network) are now the intended default
landing experience, not compute. This ADR revisits only that one default — `initialActiveView`'s
derivation mechanism (`homeEmphasis` → view, with fallback to the first enabled view) and every
other decision in ADR-260065 (formula builder, payload helpers, badges, "Explain this value",
Flow visualization, `computeBadges` gating) are unaffected and remain in force.

## Decision

Flip the shipped default of `DEFAULT_HOME_EMPHASIS` (`src/ui-shell/use-preferences.ts`) from
`'compute'` to `'relationship'`. Consequently `initialActiveView` now lands new/never-toggled
users on **Network** by default; Flow remains one click away via the view tabs, and users who
already set an explicit preference are unaffected (the preference is user-owned, not a decree
that overwrites a chosen value). The `homeEmphasis` → view mapping itself (`compute` → Flow,
`relationship` → Network, fallback to the first enabled view) is unchanged — only the default
value assigned to the preference changes.

## Alternatives Considered

- **Leave `compute` as the shipped default and let users opt in to Network:** rejected — the
  point of this change is that Network should be what new users see without configuration.
- **Remove `homeEmphasis` and hardcode Network:** rejected — the preference and its Compute-tab
  consumers (badges, emphasis toggle in `PreferencesPanel`) stay meaningful; removing the
  contract would be a larger, unrelated interface change.

## Consequences

- Positive: new sessions land on Network by default, matching current product direction.
- Negative: none functionally — this is a one-constant flip. Documentation/comments in
  `use-preferences.ts` and `architecture.test.ts` that described the `compute` default as the
  Q3-driven baseline needed updating to avoid describing stale behavior.
- Risk (carried over from ADR-260065, unchanged): the preference is written to localStorage on
  first render, so it is sticky per browser — a user who loaded the app under the old default
  and never toggled the preference already has `'compute'` persisted and will not pick up this
  new default. This is pre-existing behavior of the preferences store, not introduced here.

## Verification

- Unit: `use-preferences.test.tsx` asserts the default `homeEmphasis` is `'relationship'`.
- Architecture: `architecture.test.ts`'s preferences-store assertion checks
  `DEFAULT_HOME_EMPHASIS` against `'relationship'`.
- Component: `WorkspaceShell.test.tsx`'s default-view tests assert Network renders (not Flow)
  under the default preference, and that the Flow canvas is not present by default.
- E2E: scenarios that already primed `relationship` explicitly via `addInitScript` were
  unaffected. Four scenarios relied on the old shipped default implicitly and needed updates:
  `graph-workspace.spec.ts` ("shows Flow view as default…" now primes `compute` explicitly via
  a new `primeComputeEmphasis` helper and is renamed; a new default-is-Network scenario replaces
  it; the ArrowLeft/ArrowRight keyboard-navigation scenario's expected tab order was reordered
  around the new Network-first default), `workspace-preferences.spec.ts` (the emphasis-switch
  scenario now starts from Network and switches to Flow, inverted from before), and
  `compute.spec.ts` (the Flow-badge scenario now primes `compute` explicitly since badges only
  stamp on Flow's node seam, not Network's).

## Rollback

Flip `DEFAULT_HOME_EMPHASIS` back to `'compute'` in `use-preferences.ts` and restore the three
test expectations this ADR updated. No schema, contract, or data-migration involvement.
