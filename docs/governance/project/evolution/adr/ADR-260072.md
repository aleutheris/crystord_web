# ADR-260072: Flow View Edge Direction — Value Flow, Not Dependency Reference

Status: Accepted
Date: 2026-08-26
Owners: Crystord App maintainers (info@aleutheris.com)

> Supersedes ADR-260039 §D1/§D5 only (edge direction is now specified explicitly). ADR-260039's
> other decisions — eligible-bond projection scope, left-to-right-only orientation, the relayout
> contract, and arrowhead/label/handle grammar — are carried forward unchanged. Per the artifact
> model's whole-record-supersede rule, this record is the single source of truth for Flow-view
> edge direction; ADR-260039 is retained in place (not moved to `adr/superseded/`) because
> REQ-FR-260045, REQ-FR-260046, and BI-260044 still reference it for the decisions this ADR does
> not touch.

## Context

ADR-260039 formalized that Flow-view edges render with visible arrowheads (D5) but never
specified what the arrow direction is supposed to *mean*. In practice, `atomsToFlowEdges`
rendered the raw `OP_DEPENDENCY` bond pointer unmodified: a bond with `direction: "from"` on
atom A pointing at atom X means "A depends on X" (`docs/user-guide.md` §Bonds), and the edge was
built as `source: A, target: X` — arrowhead landing on the dependency.

That is the correct direction for a generic dependency-reference graph (the same convention as
an npm or Make dependency graph: the arrow points from the thing that needs something to the
thing it needs). It is backwards for a diagram whose stated purpose (ADR-260039: "a
readability-first directional flow diagram") is to show how *data* moves through a computation.
An Atom's `content` is computed at retrieval time *from* its dependency chain
(`docs/user-guide.md` §"How The Data Is Structured" / evaluation section) — the value flows from
the dependency into the computed atom, the reverse of the bond pointer.

Combined with the left-to-right longest-path layering in `use-flow-layout.ts` (root layer = nodes
nothing points at, i.e. typically the final/top-level computed atoms), the un-inverted direction
placed final results on the left and raw inputs fanning out to the right, with arrows pointing
away from results toward their inputs — the opposite of how a left-to-right flow diagram is
conventionally read (inputs → transformation → outputs).

Network view has the same underlying bond data but is explicitly a generic relationship graph
(ADR-260028), not a flow diagram, and correctly keeps the raw bond-pointer direction — this
decision does not change Network view.

## Decision

1. **Flow-view edges represent value flow, not the dependency-reference pointer.** For a bond
   with `direction: "from"` on atom A pointing at atom X (A depends on X), the Flow-view edge is
   built with `source: X, target: A` — the dependency is the source, the dependent computed atom
   is the target. The arrowhead lands on the atom that consumes the value.
2. **Network view is unchanged.** `atomsToEdges`/`atomsToNetworkEdges` keep the raw bond-pointer
   direction (`source` = the atom declaring the bond, `target` = the atom it points at). Network
   view answers "who references whom"; Flow view answers "what feeds what" — the same underlying
   bond data legitimately renders in opposite directions in the two views.
3. **`use-flow-layout.ts` is unchanged.** Its longest-path layering already operates purely on
   whatever `source`/`target` it's given; inverting the edges upstream in `atomsToFlowEdges`
   naturally flips the layering to place raw inputs at layer 0 (left) and downstream computed
   results fanning out to the right, matching conventional left-to-right flow-diagram reading.
   No change to the layout algorithm itself.
4. **Cycle-edge matching is inverted to match.** The backend reports `cycleEdges` as `{from, to}`
   in the raw dependency-pointer direction. `cycleEdgeKeys` now builds its match keys as
   `to->from` so `applyCycleStyling` still lines up cycle-danger styling with the edges Flow view
   actually renders.

## Alternatives Considered

- **Leave Flow view showing the dependency-pointer direction, document it as "who depends on
  whom" instead of "value flow":** rejected — the view is explicitly positioned as a flow/data
  diagram (ADR-260039 context, view label "Flow"), and users read arrows as showing movement of
  data by default; keeping the reference-graph convention there is a readability trap the ADR-039
  process didn't catch because it only specified arrowhead *visibility*, not *meaning*.
- **Add a per-view direction toggle:** rejected as unnecessary scope — Network and Flow already
  serve the two directions users need (reference graph vs. value flow); a toggle duplicates that
  distinction without adding capability.

## Consequences

- Positive: Flow view's arrows and left-to-right layering now match the conventional reading of a
  data-flow diagram (inputs on the left, results fanning right, arrows pointing toward the
  consumer). No backend or schema change required — `direction` semantics are unchanged; only the
  Flow-view edge construction inverts them for display.
- Negative: Flow-view edge direction now diverges from Network view's edge direction for the same
  bond data, which is intentional (§2) but worth calling out to avoid future "these don't match,
  is that a bug?" confusion — this ADR is that answer.
- Risks: any future Flow-eligible bond type added to `FLOW_ELIGIBLE_BONDS` (currently only
  `OP_DEPENDENCY`) must be checked against this same value-flow-vs-reference distinction before
  assuming the inversion is universally correct for it.

## Verification

- Unit: `atomsToFlowEdges` produces `source: bond.uuid, target: atom.uuid` for an eligible
  `direction: "from"` bond (`graph-types.test.ts`).
- Unit: `cycleEdgeKeys` emits `to->from` keys so `applyCycleStyling` still danger-styles the
  correct (now-inverted) Flow edges.
- Regression: full unit suite (1894 tests) and architecture tests pass unchanged elsewhere;
  Network view's edge direction and tests are untouched.

## Rollback

Revert `atomsToFlowEdges`'s `source`/`target` assignment and `cycleEdgeKeys`'s key order to
restore the pre-ADR-260072 (dependency-pointer) direction. `use-flow-layout.ts` requires no
rollback — it is direction-agnostic.
