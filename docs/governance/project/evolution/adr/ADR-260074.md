# ADR-260074: Left Rail Width — CSS-Only Reactive Cap on Viewport Resize

Status: Accepted
Date: 2026-08-27
Owners: Crystord App maintainers (info@aleutheris.com)

> Approval note: accepted 2026-08-27 on the project owner's explicit real-time approval, given
> during the post-implementation review of EPIC-260077 / ADR-260073.

## Context

ADR-260073 (D2) bounds the left rail's width to `[200, min(480, 0.6 * viewportWidth)]`, but
applies that clamp only at the moment the width *changes* — drag, keyboard step, reset, or
read-on-mount. Its Consequences/Risks section explicitly accepts that a bare browser-window
resize, with no other interaction, does not re-clamp an already-persisted width: "the cap is
applied at the moment width changes... not on a live `window.resize` listener... a deliberate
scope boundary, not an oversight."

That framing considered the cost of a JS `resize` listener and judged it not worth the
complexity for a minor cosmetic edge case. It did not consider a zero-JS alternative: a plain
CSS `max-width` alongside the existing `width`, which the browser re-evaluates on every layout
pass with no listener at all. This ADR closes that gap.

## Decision

`LeftRail.tsx`'s `<aside>` gains `maxWidth: 'min(480px, 60vw)'` alongside its existing
`width: railWidth`. `width` remains the JS-computed, clamp-on-interaction value from
ADR-260073 D2 unchanged; `maxWidth` is a second, purely presentational cap that the browser
continuously re-enforces as the viewport changes, with no `window.resize` listener and no
change to any of ADR-260073's state, persistence, or interaction decisions (D1, D3–D7 all
carry forward unchanged).

The `480px` half of the CSS expression reads from the same `LEFT_RAIL_MAX_WIDTH` constant the
JS clamp uses; the `60vw`/`0.6` half cannot be shared across a CSS string and a JS number and
must be kept in sync by hand (flagged with a code comment at the point of use).

This only fixes the *rendered layout* staying within bounds. The persisted `leftRailWidth`
preference value itself is still not re-clamped by a bare resize — it still only re-clamps at
the next drag/keyboard/reset/read-on-mount interaction, per ADR-260073 D2. A consequence:
`aria-valuenow`/`aria-valuemax` (both driven by that JS state) can still momentarily disagree
with the CSS-capped rendered width after a resize with no other interaction, until the next
interaction reconciles them. This residual gap is accepted as minor and out of scope for the
same reason ADR-260073 accepted the original risk — reintroducing it as a "fix" for the ARIA
value alone would require the very listener this ADR avoids.

## Alternatives Considered

- **A live `window.resize` listener re-clamping `leftRailWidth` state:** rejected — this is the
  option ADR-260073 already declined, for the same reason (added complexity for a cosmetic
  edge case); the CSS-only option makes that listener unnecessary for the layout risk it was
  weighed against.
- **Do nothing (leave ADR-260073's accepted risk as-is):** rejected on review — the CSS fix
  costs nothing (no new state, no new listener, no behavior change to persistence or
  interaction), so there is no real tradeoff being avoided by leaving it.

## Consequences

- Positive: the rail can no longer visually crush the center canvas past the 60vw/480px
  invariant on a bare window resize; zero added JS, zero new state.
- Negative: a second place (a CSS string) now encodes half of the same bound the JS clamp
  encodes, with no automated check that they stay in sync — mitigated with a code comment, not
  a shared source, since CSS can't reference the JS constant directly for the `vw` term.
- Risks: `aria-valuenow`/`aria-valuemax` can still momentarily lag the CSS-capped rendered width
  after a bare resize (see Decision) — accepted, not fixed, to keep this a zero-JS change.

## Verification

- Unit: `LeftRail.test.tsx` asserts the `<aside>` carries the `maxWidth` style.
- Regression: full existing left-rail unit and e2e coverage stays green (no interaction/
  persistence behavior changed).

## Rollback

Remove the `maxWidth` style property from `LeftRail.tsx`'s `<aside>`; the rail reverts to
ADR-260073's original behavior (cap enforced only at interaction time).
