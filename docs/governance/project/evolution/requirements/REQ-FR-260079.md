## Statement

The system shall allow a user with edit access to arrange category dimensions into a
single-parent hierarchy from the Categories navigator: creating a dimension beneath a chosen
parent, attaching an existing dimension to a parent, and detaching a dimension back to a root —
with dimensions rendered as a tree of roots and their nested children. Nesting is always expressed
from the child (to place B under A, edit B).

## Rationale

The category model is the user's own taxonomy, and real taxonomies nest (`Region ▸ Country`).
The navigator shipped dimensions as a flat list (ADR-260064 §1), so structure could not be
expressed at all, and the only "key + display name" form under a dimension created a *value* —
which users read as dimension creation. The backend has supported the hierarchy since schema
9.2.0 (`createCategoryDimension(parentDimensionKeys…)`, `connect`/`disconnectCategoryDimensions`,
`CategoryDimensionOutput.parentDimensionKeys`); the capability was simply never exposed, and
`parentDimensionKeys` was fetched and discarded.

## Acceptance Criteria (behavioral)

- Creating a dimension with a parent selected produces a dimension nested under that parent, in
  one operation, with no intermediate root state.
- The navigator renders dimensions as a tree: roots at the top level, children nested beneath
  their parent; a nested dimension lazy-loads its values on expand exactly as a root does.
- An existing root dimension can be attached under a parent, and any dimension can be detached
  back to a root.
- Candidate parents are presented in tree order and indented by depth, so two similarly-named
  dimensions in different branches are distinguishable.
- Moving an already-parented dimension to a different parent succeeds from the user's point of
  view as a single action, and when the underlying two-step operation fails partway the resulting
  state (dimension left as a root) is reported rather than silently presented as success.
- Attempting to give a dimension a second parent, or to form a cycle, is refused with a readable
  message rather than a raw error code.
- Existing flat dimensions continue to function as roots with no migration.
- Edit affordances appear only for nodes whose real `accessLevel` is OWNER or EDITOR; the **move**
  affordance additionally requires OWNER, since re-parenting is owner-only server-side and an
  EDITOR grant would fail with an error that cannot be distinguished from a missing dimension.
- Candidate parents are not filtered by access level: read access suffices on a parent, and every
  dimension the server returns is already readable.
- Filtering behavior is unchanged: OR within a dimension, AND across dimensions, and
  `includeDescendants` applying to values only — selecting a parent dimension does not implicitly
  include child dimensions' values.
