## Statement

The system shall provide a **Compute** inspector tab through which the user authors an atom's
operation without typing JSON — choosing a function from the discovered operations, filling
argument slots with atom references picked by title or constant keys, and configuring COLLECT
via a registered query name plus that query's own filter (label chips, or a category
dimension/value pair) — shall render computed atoms' content
read-only with a convert-to-manual escape, shall explain the atom's evaluation state in plain
language, and shall visualize computation status in the Flow view via node badges and cycle
highlighting, honoring the compute-emphasis preferences.

## Rationale

The compute engine is the product's differentiator (Q3) yet is invisible: no way to author an
operation, no visibility into evaluation success or failure. A builder plus plain-language
explanation makes derived values authorable and self-explaining with the current stack — no
charting library (REQ-CR-260010).

## Acceptance Criteria (behavioral)

- The Compute tab lists discoverable operations; the five built-ins enforce their arity
  (SUM 1+, MINUS 2, PRODUCT 2+, DIVIDE 2, COLLECT 1 query + constants); unknown operations
  remain editable via a generic argument list.
- Argument slots accept atom references picked by title from the working set (stored as
  UUIDs, rendered as titles with a shortened-UUID fallback) or constant keys from the
  constants editor; each registered COLLECT query presents its own constants editor —
  `atoms_with_labels` the shared label chip editor, the category queries a dimension picker
  and a dependent value picker.
- Category COLLECT queries are configured by selection, never by typing a key. The value
  picker is scoped to the chosen dimension and resets when that dimension changes; a stored
  `dimension_key`/`value_key` that no longer resolves in the caller's taxonomy stays visible
  and selected rather than being silently replaced by another option.
- A COLLECT query with a known required constant cannot be saved with that constant empty:
  `atoms_with_labels` requires at least one label; `atoms_in_category_value` and
  `atoms_in_category_subtree` each require both `dimension_key` and `value_key`. The builder
  blocks the save with a stated reason. **Rationale under the pinned 9.3.0 contract:** the
  backend itself rejects empty required constants — absent gives
  `OP-COLLECT-CONSTANTS-MISSING`, present-but-empty/wrong-type/under-`minItems` gives
  `OP-COLLECT-CONSTANTS-INVALID`, and in both cases no query runs and no rows are returned;
  "an empty filter never means 'match everything'" (`user-guide.md:1305`). The client gate
  therefore prevents the user saving an atom **certain to fail evaluation**, and applies
  identically to both query families — the two messages differ only in the action they ask
  for. Queries whose requirements the client does not know (free-text) are not gated.
- A category COLLECT cannot be saved against a category value the caller does not **own**.
  `retrieveCategoryValues` returns owned *and granted* taxonomy, but the category queries
  resolve owned values only (`user-guide.md:1320`), so a granted value passes the backend's
  constants validation, runs, and returns an empty list — **succeeding silently**. This is the
  one COLLECT path that can still be quietly wrong, so non-owned values render disabled and the
  save is blocked. The dimension picker is deliberately **not** filtered: the dimension is
  matched by key, so a granted dimension is legitimately usable.
- Chip-editor text that the user typed but has not committed with Enter is included in the
  save rather than dropped (ADR-260027 D2, applied to the compute surface).
- The formula summary distinguishes a filtered COLLECT from an unfiltered one — it renders
  the collected labels, or the `dimension_key ▸ value_key` pair for a category query, or
  names their absence, and renders the query name verbatim rather than through the
  atom-reference shortener. Category pairs render by key: the summary is pure and has no
  taxonomy to resolve display names against, and the query name itself carries the
  exact-value-vs-subtree distinction.
- Saving writes the canonical operation payload through the shared update mutation; the user
  never sees or types the JSON.
- A computed atom's content is read-only in the Details and Table surfaces; the Compute tab
  offers a confirmed "Convert to manual" that clears the operation and restores editing.
- "Explain this value" renders each evaluation state in plain language, naming failing
  inputs and cycle members by title where resolvable.
- Computed atoms in the Flow view carry a status badge (always, or only when selected, per
  the `computeBadges` preference); cycle members and cycle edges are visually flagged.
- The initial active view derives from `homeEmphasis` (`compute` → Flow, `relationship` →
  Network, falling back to the first enabled view).
- Viewer-level atoms expose no compute editing (respects ADR-260059).
