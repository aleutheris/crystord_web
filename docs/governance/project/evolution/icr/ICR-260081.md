## 4. Proposed Change

- Proposed behavior/signature: adopt backend GraphQL schema **9.3.0** as the pinned contract and set
  `backendSchemaRange: "~9.3.0"` (auto-adopt `9.3.x` patches; a higher minor/major requires a new ICR).
- **Net schema delta, 9.2.0 → 9.3.0 (from the bundle diff):** purely **additive**, entirely on the
  operation-discovery surface (attributed to backend `ICR-260018` per the schema's own comments):
  - New query: `collectQueries: [CollectQueryInfo!]!` — the whitelisted COLLECT queries with their
    required constants, derived from the server's registry.
  - New non-null fields on existing **output** type `OperationFunction`: `minArity: Int!`,
    `numericOnly: Boolean!`; plus nullable `maxArity: Int` (null = unbounded).
  - New types `CollectQueryInfo` (`name`, `description`, `constants`) and `ConstantSpec`
    (`key`, `type`, `minItems`).
  - **No removals, renames, signature changes, or newly required inputs** anywhere in the diff.
- Change type: `additive`.
- **Distinction from ICR-260002:** that delta landed entirely *outside* the frontend's used surface.
  This one does **not** — `OperationFunction` is a type this frontend actively consumes via
  `DISCOVER_OPERATIONS_QUERY`. It remains backward-compatible because the additions are new fields on
  a *return* type and GraphQL delivers only the fields a client selects; that query
  (`src/api-contract/compute-operations.ts`) selects `name` and `description` only, so its response
  shape is unchanged. This is recorded explicitly because it narrows the "additive ⇒ no impact"
  argument to "additive on a return type ⇒ no impact *given the current selection set*".
- Why a new ICR is required: the `~9.2.0` pin authorized by `ICR-260002` auto-adopts `9.2.x` patches
  only; `9.3.0` is a minor bump and falls outside `>=9.2.0 <9.3.0`. This ICR ratifies the `~9.3.0` pin.

## 5. Impact Analysis

- Technical impact: the `backendSchemaRange` pin only. No frontend code change is required — verified
  by grep that `collectQueries`, `CollectQueryInfo`, `ConstantSpec`, `minArity`, `maxArity`, and
  `numericOnly` appear **nowhere** in `src/`.
- Consumer impact: **none** for `crystord_app`. The used surface is unchanged in wire shape.
- Operational impact: **this pin is required, not discretionary.** The repository owner reports
  (2026-08-29) that all production servers now run `9.3.0`. Under the previous `~9.2.0` pin every such
  environment fails the startup handshake at `src/api-contract/schema-compatibility.ts` and renders
  `SchemaErrorScreen` instead of the workspace. Conversely, this pin now *excludes* any `9.2.x`
  backend — a rollback of the frontend alone is not sufficient (see §7).
- Reference-document impact: installing the v9.3.0 bundle updates `docs/crystord_server/schema.graphql`
  (`64d2d8b6…` → `ae7b6ef6…`) and `docs/user-guide.md`; the bundled
  `schema-compatibility-contract.md` is unchanged from 9.2.0. These are development-time references
  and are **not** inputs to the runtime handshake, which compares the live `schemaInfo` response
  against `backendSchemaRange` only.
- Risks: low. Residual risk is that a future `9.3.x` patch touches the used surface — bounded by the
  `~9.3.0` range (patch-only auto-adoption) and the fail-fast handshake.

- **Retrospective note (2026-08-31, added by EPIC-260082).** The "purely additive" finding above is
  accurate about the **GraphQL schema** and was the right call for the pin. It is nevertheless
  incomplete as an impact analysis: the same 9.3.0 bundle carried a **behavioural** change that no
  schema diff can surface, because it lives only in `docs/user-guide.md`. Commit `7d0b6de` rewrote
  the COLLECT `Parameters` paragraph (`user-guide.md:1305`) to specify that empty required
  constants now fail evaluation — "an empty filter never means 'match everything'" — reversing the
  wildcard behaviour that caused the LRN-003 field defect. EPIC-260082 consequently shipped code
  comments, user-facing copy, and a ratified acceptance criterion asserting the old behaviour.
  **Adopted for future adoption ICRs: diff `user-guide.md` alongside `schema.graphql`, and re-check
  any client-side rationale that asserts backend behaviour.** See LRN-003 §8.

## 7. Migration Plan

- Step-by-step migration: set `backendSchemaRange` to `~9.3.0` in all three `deploy_config.json`
  profiles (`local`, `aleuhouse`, `nucubuntunl`); `public/config.json` is **generated** from that file
  by `scripts/config.mjs` at build/serve time and needs no separate edit.
- Validation checkpoints: lint, typecheck, full unit suite, and build green against the `~9.3.0`
  config; `schemaInfo` handshake green against a live 9.3.0 backend.
- Rollback plan: revert `backendSchemaRange` to `~9.2.0` and redeploy the prior artifact (viable only
  while a 9.2.x backend is reachable).
